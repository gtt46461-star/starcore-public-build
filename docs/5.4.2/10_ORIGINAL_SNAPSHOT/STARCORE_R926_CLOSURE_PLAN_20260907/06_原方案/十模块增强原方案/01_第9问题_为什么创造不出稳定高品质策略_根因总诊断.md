# 第9问题：为什么创造不出“高胜率、高稳定、高品质策略”——根因总诊断

## A. R924已经具备什么
R924并非“创造功能空壳”：
- 算法Genome、DSL/VM、结构哈希/行为哈希存在；
- 赛前冻结、开奖后结算、Future-OOS证据、Brier/ECE/Wilson、Regime、Paired、FDR、MaxMiss存在；
- 153算法、252创生资产、1852公式规模已经形成；
- FTRL、TinyDeep、离线96→64→32→100网络均存在；
- AlgorithmProductionGovernorR915已经能对完整1200动作表做“主链分数+已证书算法分数”的受控融合；
- 但当前certified=0、challenger=0、生产贡献=0。

所以核心不是“不会创造”，而是“创造→验证→修复→晋级→生产”的闭环效率和语义一致性有硬缺口。

## B. 十个根因

### 根因1：离线Action Ranker训练语义与生产1200动作语义不一致
R924的 `v51_training_core.py::action_surface()` 从每个位置取号码Top3，最终每期形成10个位置候选；`v50_train_pipeline.py`同样明确写了within_issue_action_group_size=10。
而生产主链是 `10 * C(10,3) = 1200` 个动作。
结果：
- 离线训练的“Ranker”学习的是10个位置候选排序；
- 生产 `V51ActionRankerEngine/K3ActionSpaceEngine` 面对的是1200动作；
- 训练指标不能直接证明生产排序；
- Ranker artifact长期 `PROVEN=false` 是合理结果。
R925必须重建“真实1200动作groupwise数据集与训练器”。

### 根因2：production parity没有闭环
`v51_training_core.py` 当前末端 `production_parity = False`，随后 `model_gate = quantitative_gate and production_parity`。
这意味着即使全部量化指标过关，model gate仍不可能为true。
必须增加：
- Python reference inference；
- Java host inference；
- Android inference；
- 同一冻结输入的逐动作score/probability/rank/selected结果hash；
- bit/epsilon parity；
- 通过后由不可变parity certificate写入artifact manifest，而不是手改布尔量。

### 根因3：训练入口多，但训练核心高度集中，审计边界不够清楚
`train_v51_expert_gate.py`、`train_v51_action_ranker.py`、`train_v51_selected_calibration.py`等大量入口只是调用 `stage_entry()`。
这不是错，但会导致：
- 每个阶段没有独立input/output contract；
- 容易“所有阶段其实跑了一次大pipeline，却看起来每个都独立证明”；
- 失败时难以精确定位 NumberQ、Gate、Ranker、Calibration 还是Policy。
施工必须把每阶段拆成独立数据集、artifact、manifest、metrics、parity、证书。

### 根因4：基础主链本身没有证明出显著优势
严格OOS总样本约1967，命中率约30.30%，固定K3随机基线为30%。
这说明当前fallback主链没有被统计证据证明存在稳定正优势。
创造算法如果一直以“接近随机的主链”作为teacher/baseline/paired reference，搜索会非常困难。
必须先把：
NumberQ → 1200 Ranker → SelectedHitP → Selective Policy
训练成可证明的Champion，再谈“发明算法对Champion的增量”。

### 根因5：候选容量MAX_RUNNABLE=8，证据生产速度太低
`AlgorithmEvolutionLifecycleR912.MAX_RUNNABLE = 8`。
大量候选进入 `PAUSED_CAPACITY`，而证书要求Future N≥240、Paired≥120。
如果每期只能冻结极少数候选，且后台/预测覆盖曾经不连续，则绝大多数候选永远积累不到足够证据。
解决方法不是简单把8改成100，而是“多层资源调度”：
- Tier-A精英8：完整1200动作运行；
- Tier-B候选24：共享特征/批量VM运行；
- Tier-C苗圃64：低成本代理评分；
- 只有证据/新颖度/互补度达到阈值才升层。
这样增加证据吞吐而不拖垮一分钟主链。

### 根因6：淘汰把“基础设施没捕获”与“算法质量差”混在一起
`AlgorithmEvidencePolicyR912` 在 n≥120 且 coverage<0.60 时直接PRUNED。
但 `coverage` 受：
- predraw capture是否执行；
- MAX_RUNNABLE容量；
- 后台中断；
- 版本启动边界；
- runtime pressure
影响。
因此历史中类似 N≈196、HR≈40.31%、ECE≈0.031、FDR≈0.051 的候选可能仅因coverage≈44.95%被永久淘汰。
R925必须拆：
- system_capture_coverage
- candidate_execution_coverage
- candidate_selection_coverage
- eligible_opportunity_coverage
只有“算法自己在有执行机会时长期拒绝/失败”才属于算法coverage质量；系统漏捕获不得永久PRUNE。

### 根因7：PRUNED后原始淘汰原因被覆盖
`AlgorithmEvolutionLifecycleR912` 当前生命周期语义是不可逆prune，并容易只留下 `IRREVERSIBLE_EVIDENCE_PRUNE`。
结果用户只看到“被淘汰”，不知道最初到底卡：
- Wilson
- rate
- Brier
- ECE
- Regime
- MaxMiss
- Paired harm
- coverage
还是基础设施。
R925必须永久保存 first_prune_reason / metrics / policy_version / issue / system_state，并允许“基础设施类误杀”进入RECONSIDER队列。

### 根因8：子代证据重置正确，但父代研究资本利用不足
新结构必须N=0，这是严格Future-OOS的正确做法。
问题是R924更偏“不断造新孩子”，没有充分利用父代已有100~300期证据进行定向修复：
- 哪个Regime失败？
- 哪种miss motif集中？
- 哪些原子造成校准偏差？
- 哪些动作邻域持续错？
R925必须建立 Elite Repair Pool：
父代证据不传给子代，但用于选择“只改变哪个模块/原子/门”的最小修复操作，再用paired Future-OOS验证修复是否有效。

### 根因9：多重比较FDR与家族重复导致大量候选难以过关
当前算法搜索同时存在大量同源结构；R912 `FAMILY_HYPOTHESES=48`采用保守乘法式上界。
如果大量候选只是同一家族的轻微变体：
- FDR惩罚大；
- 新颖度表面高，行为高度相关；
- 搜索预算被重复假设消耗。
R925改成两级：
1. family-level hypothesis；
2. family内候选；
并以 structural_hash + behavior_hash + prediction disagreement + paired residual correlation 做去重，只保留真正互补的family champion。

### 根因10：创造目标函数不够“生产化”
目前创造/公式体系强调结构、新颖、失败向量，但最终应优化的是：
- 严格Future-OOS选中命中率；
- Wilson下界；
- Paired improvement；
- Brier/ECE；
- Regime/block稳定；
- MaxMiss；
- Coverage；
- 延迟/内存；
- 对Champion的正交增量。
R925要建立多目标Pareto/lexicographic目标，而不是“生成更多结构”。
第一层先禁止劣质：
PIT、leakage、non-deterministic、资源超限、重复结构；
第二层再比较：
Paired/Wilson/Calibration/Regime/MaxMiss；
第三层才比较复杂度和新颖度。

## C. 最终判断
R924“会创造”，但不具备已证明的“稳定持续创造高品质策略”的闭环能力。
R925要把重点从：
生成数量 → 高质量证据收敛
随机变异 → 失败定向修复
全局永久淘汰 → 质量淘汰/证据暂停分离
10候选训练 → 真实1200 groupwise训练
人工parity状态 → 自动parity证书
单一小样本高HR → 多维Future-OOS证书
