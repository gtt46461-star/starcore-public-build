# 后台完美运行闭环施工方案

## 当前状态
代码层已经有 ForegroundService、WakeLock、BootReceiver、JobScheduler、Alarm、内部Watchdog、恢复lease；但物理设备未证明，且当前设备电池无限制=NO。因此不能称“完美后台已完成”。

## 施工原则
后台完美不是“Service活着”，而是以下完整业务链持续发生：
`FETCH -> canonical draw -> settle t -> resolve t+1 -> analysis request -> single-flight compute -> canonical commit -> predraw research freeze -> later exact settlement/OOS -> research update`

## P0拆分
1. Database critical startup轻量化：Research/历史大Schema不阻塞主链。
2. Service启动后先建立heartbeat与最小DB，再抓最新开奖、结算、排下一期。
3. 所有后台机制只负责“唤醒/重入同一Owner”，不得各自创建第二预测/第二BET/第二结算。
4. 每个阶段持久化`pipeline_event`，避免只看内存状态。
5. Recovery事件持久化：boot/taskRemoved/job/alarm/process restart/manual。
6. WakeLock只包围必要工作段，记录acquire/release/timeout。
7. 网络主/备源：记录provider、requestAt、responseAt、payload hash、canonical冲突。
8. 定义steady-state SLA：fetch<2s、queue<0.5s、compute<3s、commit<0.5s、total P95<=5s。
9. 冷启动单独SLA：不得混进稳态P95。

## 真机验收
- 亮屏连续120期
- 息屏连续120期
- 从最近任务划掉后30期
- 锁屏+Doze
- 进程被系统回收后恢复
- 网络断开/切换主备
- 充电/不充电
- 24小时soak
每一期都必须有pipeline row；覆盖>=99%，重复预测=0、重复结算=0、非法REAL=0。
