# STARCORE 分段满血施工与分段回复执行规范 V1.0

> 用途：以后所有 STARCORE / TIANSHU 版本升级、返修、分批施工统一按本规范执行。用户只需说“按分段满血施工规范继续第X批”，不得重新解释、不得重置已经完成的工作。

## 1. 总原则

1. **以真实工程状态为唯一真相**：不以文字描述、文件名、计划表或“看起来完成”代替实际源码、编译、测试、APK和哈希证据。
2. **禁止半成品冒充完成**：某批未通过全部验收门时，只报告真实百分比，不封“100%完成总包”。
3. **禁止空壳/占位/无效代码**：新增类必须有真实调用者、真实输入输出、真实状态或持久化、真实错误处理和对应测试；无主链连接的展示类不能算功能完成。
4. **禁止补丁堆叠式返修**：先读完整调用链和职责，再决定保留、拆分、重写或删除；能根治的不得继续在同一巨型方法后面叠新分支。
5. **代码量不作为唯一完成标准**：超级功能必须由完整系统实现（数据→特征/因子→训练/研究→推理→决策→持久化→UI/报告→测试），但DTO、接口、枚举、薄委托不强行凑几千行。禁止用垃圾代码凑“满血”。
6. **不伪造真机/未来数据证据**：Host、合成数据、模拟SQLite通过，不得写成Android真机通过或Future OOS已证明。

## 2. 每个批次开始时必须固定的基线

每批开工必须生成并保存：

- 基线版本名 / versionCode / applicationId / DB_VERSION。
- 基线Git commit/tree SHA（若GitHub缺基线对象，明确记录缺失边界）。
- 基线完整源码SHA256清单。
- 基线APK签名证书SHA256。
- 本批任务ID和验收条件。
- 本批目标版本，例如 `5.4.1.0.1`、`5.4.1.0.2`。
- 本批专用Git分支，禁止直接在旧main乱改。

只有基线锁定完成后才开始改代码。

## 3. 分段施工的固定顺序

每个批次内部按以下顺序循环，而不是一次性乱改：

### A. 审计
- 读取相关源码全文件。
- 建调用图、DB读写、线程、Owner、异常、资源依赖清单。
- 找重复职责、巨型方法、空catch、双写、竞态、错误Owner、旧入口。

### B. 设计
- 明确哪些文件：保留 / 拆分 / 重写 / 删除 / 新建。
- 明确唯一数据源、唯一Owner、事务边界和失败恢复策略。
- 明确兼容旧数据和覆盖安装路径。

### C. 真实修改
- 直接修改生产源码，不只写报告或测试壳。
- 新模块必须接进真实主链。
- 旧重复链路必须删除、降级为薄委托或明确废弃。
- 每完成一组相关文件立即做最小编译/静态门。

### D. 小闭环验证
- Java编译。
- Host Harness。
- SQLite/事务/故障注入。
- 资源ID/manifest身份。
- 必要时反解DEX确认最终APK里真的有新类和调用。

### E. 再继续下一组
只有上一组没有破坏现有主链后，才进入下一组。

## 4. 进度百分比规则

进度不按聊天条数、代码行数或耗时计算，而按**任务验收权重**计算。

每个任务只能处于：

- `NOT_STARTED`
- `PARTIAL`
- `PASS`
- `BLOCKED_EXTERNAL`（仅限真机、未来数据等外部证据）

批次百分比 = 已完成验收权重 / 本批总验收权重。

### 进度汇报必须包含

`本批进度 X% | 总方案累计 Y% | PASS/PARTIAL/NOT_STARTED/BLOCKED | Java/Class | Host | SQL | APK | 真机/Future边界`

严禁为了好看把91%写成100%。

## 5. 每次分段回复固定格式

### 开始/继续时
只需要简短说明：

- 从上次真实百分比继续，不重置。
- 这一段具体关闭哪几个硬门。

### 中途更新
只有出现**真实新证据**时更新，例如：

- 找到根因。
- 完成真实重构。
- 编译通过。
- Harness通过。
- 发现新的阻断缺陷。
- APK生成/签名/反解通过。

不要重复“我正在继续”之类无信息内容。

### 一条回复结束但批次未完成
必须明确：

- 当前真实百分比。
- 已经真实修改了什么。
- 已通过哪些测试。
- 还剩什么验收门。
- **明确不输出半成品总包**。

下一条用户只需说“继续第X批”，直接续接工作树。

### 批次100%时
必须同时满足：

1. 本批全部任务PASS（外部真机项若不属于本批，不得偷换口径）。
2. 完整源码编译通过。
3. 必要Host/SQL/故障注入通过。
4. 正式APK真实构建成功。
5. APK versionCode/versionName/applicationId正确。
6. APK签名证书与覆盖安装基准一致。
7. APK ZIP/zipalign/DEX/资源ID验收通过。
8. 完整总包生成。
9. 总包内部逐文件SHA256反向验证0错误。
10. 外层ZIP完整性测试通过。

缺一项不得写“本批交付100%”。

## 6. 逐文件修改证据标准

每批必须生成逐文件变化总账，至少包含：

- 文件路径。
- 状态：新增/修改/删除。
- before SHA256 / after SHA256。
- before/after 行数。
- before/after 字符数。
- +行 / -行。
- +字符 / -字符。
- 修改职责说明。
- 对应任务ID。

生产源码变化与纯报告/测试变化必须分开统计，防止用大量报告文件夸大施工量。

## 7. 超级功能的“满血”验收方式

深度学习、动态迭代进化、创造能力、原子/分子/因子等不得用一个几十行类冒充。

必须检查完整闭环：

`原始数据/PIT → 特征/原子因子 → 质量门 → 训练/研究 → artifact/version/hash → 加载 → 推理/评分 → 决策主链 → 逐期证据 → 结算 → 学习/反推 → 生命周期/淘汰/修复 → UI独立展示 → 完整报告 → 回归测试`

任何模块没有真实主链消费者，只能标PARTIAL。

## 8. 数据库和后台类施工红线

- DB升级必须可重入、可恢复、不可wipe用户历史。
- WAL数据库备份必须checkpoint/关闭连接/校验后再迁移。
- Critical与Research不得互相拖死启动。
- canonical/settlement/event等需要一致性的写入必须同事务或可靠outbox。
- 事件账本必须可去重、乱序保护、重放、终态不倒退。
- 后台“代码存在”不等于真机后台已证明；真机证据单独记录。

## 9. APK和覆盖安装验收

正式APK必须验证：

- applicationId不变。
- versionCode严格递增。
- versionName正确。
- 原签名证书连续性PASS。
- zipalign/ZIP完整性PASS。
- 最终DEX内存在本批关键类。
- 关键生产调用确实进入DEX，不只是源码文件存在。
- resources.arsc和DEX资源ID无漂移。

## 10. “完整总包”定义（以后固定使用）

用户说“完整总包/整个软件总包”时，**不是只打当前源码+APK**，而是采用“全量继承型总包”：

1. 当前最终完整源码、res、assets。
2. 正式覆盖安装APK。
3. 当前Git历史/bundle/patch。
4. 当前验证和逐文件审计。
5. 当前施工方案和输入证据。
6. 覆盖安装签名证据；若上一总包已有私有签名包并且用户要求全量继承，则原样继承并标安全警告。
7. 上一版本完整回滚。
8. 完整构建工具链。
9. 上一总包中的原始历史包/基线/研究资产/合成验证资产等**全部继承**，不得因为“当前编译不需要”就擅自删掉。
10. 上一版本面向交付的目录可额外归档，避免任何文件丢失。
11. 根目录生成新的完整SHA256 Manifest和完整性报告。

因此，新总包原则是：**上一全量总包内容只增不漏；需要替换的当前版本目录替换后，旧版本目录归档保留。**

## 11. GitHub施工规范

- 每批创建独立施工分支。
- GitHub存在完整基线tree：直接在真实父提交上施工。
- GitHub缺少中间版本对象：不得声称完整源码已同步。
- 优先补真实版本链；若连接器无法一次上传大树，则总包必须含完整Git bundle和精确patch，并在GitHub写入同步边界记录。
- GitHub服务器证据和本地总包证据分开陈述，禁止混淆。

## 12. 失败和工具超时处理

- 命令超时 ≠ PASS，也 ≠ 源码失败。
- 将长Gate拆成独立可验证步骤重新跑。
- 构建脚本自身bug必须修脚本后从头重跑，不能跳过门。
- 遇到旧验收规则与新架构冲突，应升级验收规则到新合同，而不是删除测试凑绿。

## 13. 用户以后最简指令

### 继续当前批
`按分段满血施工规范继续当前批次。`

### 开始下一批
`按分段满血施工规范开始第X批，完成后给全量继承型总包。`

### 要求中途状态
`按规范报真实进度和当前证据。`

不需要用户再次重复“禁止空壳、禁止补丁堆叠、必须逐文件统计、必须总包、必须覆盖安装APK”等长要求，本规范默认全部生效。

## 14. 本规范的最终目标

让每一批施工都满足：

**能继续、能复现、能回滚、能验证、能覆盖安装、能逐文件审计、不能靠口头冒充完成。**
