## 3. 已落实的产品代码修改

### 3.1 CountdownClock.java：不在时钟锁内执行外部监听器

原 `tickOnceInternal()` 及手动刷新入口使用同步方法，监听器回调仍占有 CountdownClock 的 monitor。广播或监听器一旦阻塞，其他线程读倒计时状态可能也被挡住。

修改：只在 `synchronized(this)` 内投影时间、更新上次 tick 信息和复制监听器/倒计时等字段；退出锁后执行回调。保留原 Handler 调度、异常续跑、停止行为，不引入新后台常驻线程。

反例验证：旧 R977 在手动回调持锁、定时回调持锁、慢监听器阻塞读取三个断言失败；R978 的 5 项锁专项检查全部通过。另重新执行原 7 项时钟重入/异常/停止测试。这里使用明确的 Android Handler 适配层，不是手机 UI 帧率实测。

### 3.2 MainActivity.java：UI 刷新异常不再永久移除下一次 tick

原 uiTicker 的下次 postDelayed 位于普通方法尾部；中间刷新抛出异常时，可能没有下一次刷新。

修改：保留暂停/销毁防护；正常刷新放在 try 中，RuntimeException 记录 `R978_TICK_REFRESH_FAILED`；finally 再检查 resumed/destroyed/handler 后安排下一次 1000ms tick。暂停后的 Activity 不重新启动 ticker。

验证：整个产品 Java 编译、真实资源绑定检查，以及 4 项源码结构断言通过。没有把静态断言描述成 Android Activity 生命周期、UI 操作或故障注入的真机测试。

### 3.3 ResearchDynamicBootstrapR922.java：历史训练入口、公平续跑和原子进度保存

原问题 A：训练选择必须关联到 DirectedResearchCreation 的 CREATED 记录。导入或迁移的旧公式没有该关联，就可能被训练入口漏掉。

修改 A：直接从未完成历史开发训练的算法选择；排除 PRUNED、QUARANTINED、RETIRED、ARCHIVED 及已 DONE 记录。保留模型公式解析和原有数据验证，不伪造缺失的创造凭据。

原问题 B：本期已经推进过一个小分片，就从“未服务”集合中排除。一个 240 标签任务做了 4 标签不等于完成；旧行为可能迫使它继续等待新开奖。

修改 B：未完成作业在同一已知期仍可调度。保留最后父体游标和公平排序，优先照顾本期尚未得到机会的其他父体。每片最多 16 个历史行，不代表允许超出继承预算。

原问题 C：旧入口将新开发试验的数据截止固定到算法最初创造期，旧公式可能只有很少可用数据。

修改 C：新开发作业冻结到登记时最新已知的合法开奖；已存在的作业保留原 cutoff、数据哈希、输入顺序、cursor、模型参数和轨迹哈希，绝不把旧试验重标为新试验。

原问题 D：同片已有完成的数值更新，下一次外层预算 checkpoint 抛出 Yield 后，可能跳过后续原子保存，反复重算。

修改 D：已有进度时，将协作式让出转为进入统一提交出口；没有进度才向上让出。内层训练 Yield 也保留已完成前序行。cursor、n、参数状态、trace 在原事务内一起保存，提交失败一起回滚。保留 CAS/状态更新数一致性检查。

增加可核验状态：`r978_development_progress_<id>`，包括 historicalN、cursor、cutoff、stateHash，明确 `futureEvidenceAdded=0`。缺数据、容量满或输入错误按父体保存原因与 5 秒重试时间，不假装成功，不无限忙循环。

开发完成仍调用原发布流程：新子代 gen+1、DEV 指标来自实际训练，未来样本为 0；旧父体公式保留。新子代最早从允许的下一期参与后续计算/观察，不回填已开奖期预测。

### 3.4 ResearchLearningContinuityR912.java：同一期重新调度历史作业

原高优先级只照顾 lane:13 在线/训练后处理，lane:18 历史开发容易被拖后；历史分片状态可能被翻译为本期已经服务完成。

修改：优先轮次在 lane:13 与 lane:18 之间交替，另一半轮次仍按现有 22 通道轮询推进原子、分子、因果、证书等维护。历史未完成就保持 DEV_ROUND_PENDING；存在开发积压也启用优先轮次。即使 served_issue 已是当前期，只要 active_task_id 非空，也不能计入 PERIOD_COMPLETE。

连续性测试不直接调用 trainSlice/训练入口，也不人为替换维护任务结果：同一期只调用实际总调度器 pulse，15 次推进完成 240 次实际模型更新并生成子代。测试里的其他维护通道预置为本期已审阅，用于隔离历史作业新积压的续跑；这不是全手机所有任务同时运行的吞吐基准。

## 7. 仍然未关闭的问题与验收条件（未计入“已完成”）

### 7.1 剩余预测延迟/偶发不出号

本轮已解决可复现的时钟锁和 UI ticker 续跑风险，但没有获得修复后手机全服务 trace。原报告中的两次 16 秒级 R977 计算含未细分的 R36_COMPUTE 耗时；具体是模型加载锁、未覆盖的同步操作还是其他步骤，现有证据不足以唯一定位。不能承诺这次所有出号已达到 5 秒，或每期绝不漏出。

需要目标手机连续记录：新开奖确认→目标期解析→选模开始→模型快照完成→推理结束→唯一决策提交→UI 收到快照。每期应清楚区分等开奖/计算中/没有合格模型/故障。当前没有对全部这些生产 trace 点补齐并真机验收。

### 7.2 校准/证书/主链非零

本轮没有更改证书质量门，没有把旧不兼容研究单元拼接，也没有把 240 个训练标签当作 240 个未来验证样本。当前 V2/V3 模型实际独立样本仍少，旧算法的跨身份数据需要按真实模型、版本和数据角色追溯。证书为零不能靠强行设置 CERTIFIED 解决；安装后不保证立即有合格主链算法。

“存在满足当前资格的可执行算法，则本期选择最佳并唯一提交”有专门主链测试；它不等于“无合格算法也必须造一个出号”。本版没有实现或宣称后者。

### 7.3 整体自主进化与原子矩阵

实际 VM、矩阵梯度、原子/分子消费、连续训练和两轮进化有回归证据；但所有策略家族、公平调度在真实 CPU/数据库压力下、所有原子/因果结构、动态替代优胜率及长时间清理回收没有全面设备验收。新子代独立未来效果未知。不能把 CREATE/进化计数大于零等同于完整创造能力已经验证。

### 7.4 数据升级与设备现场

未连接手机，未在原始实际 SQLite 文件上做整库迁移/崩溃恢复（输入是检测报告导出，不是可直接启动的完整原数据库）。未测熄屏、断网恢复、系统进程回收和长期5000期存储上限。模拟重建 DbStore 和事务回滚测试不代替这些场景。
