# R69 report stop, delete and restart

The user reports that R68 cannot cancel/delete the old large report and generating a new one has no effect. The prior UI rejected cancellation of completed reports, had no explicit deletion action, and used a process-local running flag to reject later generation attempts. Automatic expiry also honored a 24-hour soft share grant, even when no reader was open. The cancellation timer could cancel the current `workerFuture` after its captured control belonged to an earlier worker, risking cancellation of a queued runnable before its cleanup/finally ran.

Changes:

- The first menu action is now **clear old reports and generate a current complete report**. A separate clear-only action and cancel-only action are available. UI polling generations detach from old status polling immediately, and the new export is submitted only after the durable clear receipt.
- Independent durable report controls stop active/queued full exports and SAF transfers. The sole existing report owner applies them before ordinary cleanup or new work. Exact request-ID removal handles requests behind the FIFO head. A generation fence prevents pre-reset in-memory observation/SAF requests from appearing after reset.
- Explicit deletion does not hash or recompress a 650 MB delivery. It bypasses soft share grants while preserving actual open reader locks. The current-job pointer is detached; the old job directory moves into a private deletion directory before cleanup so interrupted deletion resumes without a broken current-job pointer. No business database, model, retention archive, or externally saved file is deleted.
- Interactive reports and control requests can yield an active retention export. The deferred retention request remains durable and resumes later. Cooperative native/file cancellation and the catalog cancellation signal replace cancellation of a potentially newer worker Future. An old drain cannot stop a service start that arrived later.
- R68 diagnostic coverage, lossless metadata export, raw-backup separation and one-ZIP delivery remain. R65/R66/R67/R68 numeric continuation is explicitly reviewed; no certificate migration, training rule relaxation or business database schema change.

`ReportResetR69` executes actual control, queue, journal and publication code on a real filesystem. It covers a sparse 650 MiB old report, a live reader, a soft grant, queued full/SAF/retention requests, new requests admitted after the reset snapshot, cancellation in several stages, interrupted deletion, preservation of database/model/external-file sentinels, owner-lock enforcement and the actual request-generation fence. `run.py` also retains the R68 and earlier runtime/numeric/archive regressions. Synthetic filesystem tests and successful Android compilation are not phone endurance or UI acceptance.
