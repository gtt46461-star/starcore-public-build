版本：`R31.3-CONSTRUCTION-20261105`。本分册取代14、15分册的执行方式。56卡原文、全部数值阈值（`acceptance_config.json`字节不变）和资产保护要求全部保留；R31.1/R31.2控制文件分别归档于`construction/archives/STARCORE_R31_1_EXECUTION_20261105/`与`construction/archives/STARCORE_R31_2_SEQUENTIAL_20261105/`。方案修订不代表Android故障已修复。

## 1. R31.2为什么仍然推不动

对施工分支提交`293bb230`和CI运行`41987211228`的核查结果：

| 问题 | 事实 | 后果 |
|---|---|---|
| 第一批全是工具活 | S00没有一行业务代码；它的自检要先全量构建一次，再按结果写在制品清单，再构建一次比对 | 两小时只做了HOST注册表、绑定和自检脚本，S00仍未关门 |
| 开工前先要全局全绿 | S01要求整个测试套件0失败才允许第一张业务卡开工；而11项CapacityWait与Certificate失败本身就属于业务卡的修复内容 | 业务卡永远排在一个“先把所有问题修完”的门后面 |
| CI兜底本身是坏的 | 方案给的r312-gate.yml调用setup-android未指定packages，sdkmanager找不到`tools`包，40秒失败 | 本地无SDK时无法取得构建结果 |
| 方案修订弄坏Gradle | verify_baseline.py在Gradle配置阶段钉死方案清单哈希，R31.2一改方案，所有Gradle构建都失败（执行者已在293bb230改为按清单成员校验） | 施工方先修方案带来的问题 |

结论：不是“验收项太多”，而是**验收门放在了施工前面**，且门本身有缺陷。R31.3把顺序倒过来：先改代码，验收在每批末尾一次做完，历史遗留失败用棘轮逐批清偿。

## 2. 五条规则

1. **批次号就是施工顺序**：K01→K21共21批，严格依次，上一批`RECEIPT.json`提交后才开下一批。原P00–P08依赖顺序不变（`check-plan`校验）。
2. **每批的主体是改代码**：`batches/Kxx.md`直接列出本批每张卡的步骤和“文件/方法/改成什么”。写方案、改账本、重做审计都不算进度。
3. **棘轮验收，而不是开工前全绿**：
   - K01首次全量运行时，把当时所有失败登记为“已知失败”，每条指定负责修复的批次（K02–K20）。
   - 之后每批关门：不得出现新失败；本批负责的已知失败必须修好；已知失败只减不增。
   - 编译失败永远阻断；测试数不得减少，跳过数不得增加。
   - K20起已知失败和结转项必须为零。
4. **每条LOCAL验收项绑定测试**（JUnit`类#方法`或`HOST:条目`，可复用已有测试，一个测试可证多项）。确实做不完的最多结转2项：必须已提交并实际执行的红测试，写明原因，目标为后续批次且不晚于K20；结转不是PASS，到期必须通过。
5. **验收分层不变**：LOCAL 189项是关门条件；EMU 8项只在K20跑；DEVICE 24项与NATURAL 1项延后，任何批次都只能写NOT_RUN/NOT_PROVEN。发布身份冻结、r982清单、签名、APK只在K21。

## 4. 每批怎么做

```bash
G="python3 construction/STARCORE_R31_FINAL_20261104/tools/r31_gate.py"
$G status                    # 当前批、未绑定项、本批要修的已知失败、到期结转项
# 按 batches/Kxx.md 改代码、写测试；在 construction/r31/batches/Kxx/BINDINGS.json 登记
$G quick --batch Kxx         # 编辑循环：只编译+跑已绑定的测试类和HOST条目，可反复
git commit
$G close --batch Kxx         # 一次：全量构建（gradle四任务+HOST_SUITE）+棘轮判定+写RECEIPT
git add construction/r31/batches/Kxx verification/r31/batches/Kxx && git commit && git push
```

本地无Android SDK时：push后由`.github/workflows/r31-gate.yml`跑同一全量构建，下载工件，再`$G close --batch Kxx --import BUILD_SUMMARY.json`。

`BINDINGS.json`格式：

```json
{"items": {"R31-B02-C03#A3": ["com.ethk3.novaonepro.strategyv2.SomeTest#method"], "R31-B02-C02#A1": ["HOST:run_runtime_ddl_host"]},
 "known_failure_owners": {"com.x.FailingTest#m": "K02", "HOST:run_certificate_startup_host": "K04"},
 "carry": {"R31-B01-C04#A3a": {"to": "K03", "reason": "依赖下一批的fence接口", "red_tests": ["com.x.ShutdownTest#bounded"]}},
 "reassign": {"com.x.FailingTest#m": {"to": "K05", "reason": "根因在抓取路径，由B03修"}},
 "scope_extensions": [{"path": "app/src/main/java/...", "reason": "调用方随接口变更"}]}
```

`known_failure_owners`只在K01填写；`reassign`每批最多3条，只能把本批负责的已知失败推给后续批次且不晚于K20。

## 5. 防止再兜圈子

- 每批至多两次全量`close`是常态；`close`失败就按列出的问题改代码再`close`，不重写方案、不重做审计、不回头改已关批次。
- 同一源码、同一失败不重复跑CI，不重复生成证据；每批只提交BINDINGS、RECEIPT、BUILD_SUMMARY和失败日志（≤20MiB，不得夹带源码快照）。
- 某条LOCAL项在JVM/HOST上确实无法复现：先结转（带红测试），汇报原因；只有方案修订才能改变它的层级。
- 汇报只写：本批改了哪些源码文件、`close`结果、已知失败剩余数、下一批。
