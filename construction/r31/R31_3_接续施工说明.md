## 四、每批固定流程（K02起每批照做）

```bash
cd <仓库>; git checkout construction/r31-final-20261104; git pull
G="python3 -B construction/STARCORE_R31_FINAL_20261104/tools/r31_gate.py"
$G status                                   # 本批卡片、未绑定项、本批要修的已知失败、到期结转
```

1. **改代码**：打开`status`给出的`batches/Kxx.md`，按"施工内容"表逐个文件修改，同时写对应测试（`app/src/test/...`或`tools/r31/...`）。
   - 只改表里列出的文件；
   - 确需改别的文件，先在`BINDINGS.json`的`scope_extensions`写明路径和理由（不少于10个字）。
2. **重钉**：`python3 -B tools/r31/repin_scope.py --batch Kxx`。
   - 新增的生产源码文件按卡片指定角色加参数`--role 路径=NUMERIC`（或 PRESENTATION、POLICY、BUILD_CONTRACT）。
   - 输出`R31_REPIN_OK`才算完成。
3. **本地快检**（不需要SDK，几秒钟）：
   ```bash
   python3 -B scripts/r967_semantic_identity.py --check
   python3 -B tools/r31/test_verify_baseline.py
   python3 -B tools/r31/verify_baseline.py --identity-only > /dev/null && echo IDENTITY_OK
   ```
4. **绑定**：在`construction/r31/batches/Kxx/BINDINGS.json`给本批每个LOCAL项写测试，格式见`docs/16_R31.3施工推进合同.md`第4节。
   - 可以复用已有测试，一个测试可以证明多项。
   - 做不完的最多结转2项，必须带已提交且实际执行的红测试。
5. **推送并等CI**：
   ```bash
   git add -A && git commit -m "fix(r31/Kxx): ..." && git push origin HEAD:construction/r31-final-20261104
   bash tools/r31/ci_wait.sh Kxx      # 在后台运行；约20–40分钟
   ```
   - 结果会自动拉回`verification/r31/batches/Kxx/BUILD_SUMMARY.json`，失败原因看同目录`logs/gradle.log`和`logs/host_*.log`。
   - 有失败就回到第1步修代码，再重钉、再推送。
   - 只改证据或文档的推送不会触发CI。
6. **关门**：`BUILD_SUMMARY.json`的`source_head`等于最后一次源码提交，且已无本批阻断项时：
   ```bash
   $G close --batch Kxx
   git add construction/r31/batches/Kxx verification/r31/batches/Kxx && git commit -m "r31(Kxx): CLOSED" && git push
   ```
   - `close`列出问题就修代码，回到第1步。
   - **没有SDK的会话不要在摘要过期时运行`close`**，那样它会尝试本地构建并失败。
7. 进入下一批。
