## 一、为什么一直卡住、额度消耗大

| # | 原因 | 实际影响 |
|---|------|----------|
| 1 | 云端会话没有 Android SDK：`dl.google.com` 和 `maven.google.com` 被代理拦截 | 本地不能用 Gradle 编译，每次编译、单元测试、签名、模拟器都只能走 GitHub Actions，一轮约 40–60 分钟 |
| 2 | CI 产物（blob 存储）在会话内无法下载 | 只能读日志判断结果；APK 只能由用户从 Actions 页面下载 |
| 3 | 串行门禁：P03 及以后的源码施工要等 P01/P02 的 Android 和真机门通过 | 云端没有真机，这道门永远无法在会话内通过，后续 38 张卡因此长期 NOT_STARTED |
| 4 | 身份冻结链：每改一个生产源码文件，都要用 CI 的 JDK17 编译类重新冻结 r982 调用索引、R967/R82/SU1 身份，再发一次构建 | 每次小修都多一轮 CI 往返；本地 JDK21 编译结果与 CI 不等价，不能代替冻结 |
| 5 | 集成债：shared-migrations 分支单独开发，合并前没有对全量 HOST 和单元做过回归 | 合并后才暴露 5 个真实回归（红线测试、源日志前置、AtomNet 冷启动、3 个测试夹具合同），返工成本高 |
| 6 | 证据写作过重：每一步都生成大量回执和账本字段 | 大量额度花在文档上，不在代码上 |

## 二、调整后的规则（从现在起执行）

1. **验收门改为发布门，不再作开工前置。** Android 模拟器矩阵、真机、24h/72h 只在 P08/B12 发布验收时强制要求。P03–P07 的源码施工可以并行推进；未通过的门照实写在账本里，不推断为 PASS。
2. **本地优先，CI 批量。** 每批改动先用本地非权威工具链编译，并跑 HOST 和单元测试（工具在 `verification/r31/p01/local-host-matrix-015/`），失败先在本地修完。积累一组提交后，只做**一次** CI 冻结和**一次** CI 构建，不再一改一构建。
3. **身份冻结只在 CI 做。** 本地编译类与 CI 不等价，永远不用它提交 r982 冻结。冻结请求使用 `[R31_IDENTITY_FREEZE]` 任务。
4. **合并前必须做本地全量回归对照。** 任何侧分支合并前，都要在同一本地环境里对"上一个已验收版本"和"合并后版本"各跑一次全量 HOST 和单元测试。对照中新增的失败必须在合并提交里修复。
5. **卡状态口径不变，按证据逐级上升。**
   - CODE_COMPLETE：源码完成，且本地 HOST 证明通过（含反例）
   - BUILD_PASS：CI 编译、单元、lint、签名通过
   - INTEGRATION_PASS：CI 模拟器联合协议和故障矩阵通过
   - DEVICE_PASS：真机证据
6. **回执精简。** 每一组提交只写一个回执（改了什么、命令、结果、证据路径、剩余问题），不再逐步生成大文件。
7. **真机的最小条件。** 需要用户在本机用 Remote Control 共享 ADB，或提供一台可连接的 Android 设备；否则真机项一律保持 NOT_RUN。
