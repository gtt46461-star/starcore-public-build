# B01 写者与事务治理（并发集中批）

> 本批是全部“跨文件、跨线程、跨任务”的并发问题的唯一施工批次。B01 之后的任何批次不得再改锁、写者、调度归属；发现新并发问题一律回到本批次的规则处理（新开 B01-xx 子卡）。

## 1. 为什么不拆库（R29 卡死的原因与 R30 的定案）

CP06 的写入结构是：**一个 SQLite 文件 + 一把公平写锁 `DatabaseCoordinator.WRITE_LOCK_CP3`**，并且已有“关键业务写优先、后台写在关键写等待时不排队”的机制（`DatabaseCoordinator.runWrite` 第 616–717 行，`isCriticalBusinessOperationR914` / `isBackgroundOperationR909` 两份名单）。所以实时链被拖慢的根因只可能是：**某个后台写在拿到锁之后持有太久**（关键写排在它后面只能等它提交）。

R29 的做法是把 378 张表在线复制到第二个库，但 bb607cf 中有 **106 个文件、1890 处直接写研究表**（R29 施工后增至 124 个文件）、路由靠线程局部作用域，复制期间旧写者继续写 Root，于是出现 `ROOT_RESEARCH_ADVANCED_AFTER_SEAL`，CP06→CP16 连续 10 个检查点 B01 都没签收。

R30 的定案：
1. **先测量**：每一次写锁使用都记“等了多久、持有多久”（B01-01/02）。
2. **再切片**：持有超过 50ms 的后台写改成多个短事务（B01-03/04），关键写最多只等一个片。
3. **不拆库**。只有当 B10 真机数据证明切片后仍不达标，才进入条件批次 B11（只迁 r27_* 共 32 张表、停机式离线复制、冻结触发器兜底）。

## 2. 锁与线程规则（全批次、全项目强制）

| 规则 | 说明 | 检查方式 |
|---|---|---|
| L1 唯一写锁 | 所有写都经 `DatabaseCoordinator.runWrite/runAtomicWrite*`；不得新建 `SQLiteDatabase` 写连接（B11 研究库除外） | `grep -rn "getWritableDatabase()" app/src/main` 只允许 DatabaseCoordinator/DbHelper |
| L2 持锁期间禁止 | 网络请求、`Thread.sleep`、`wait/join/Future.get`、模型推理/训练、进入其他 `synchronized` | 代码审查清单；B01-01 账本 hold_max 异常即查 |
| L3 后台写持有上限 | 目标 ≤50ms，硬上限 200ms（`WriterHoldLedgerR30`） | r30_writer_hold.over_hard=0 |
| L4 让出点 | 后台切片只能在**片与片之间**让出（`ChunkedWriterR30`），事务体内部不让出（让出=回滚=白做） | ChunkedWriterR30 设计保证 |
| L5 操作名 | 后台写操作名必须以 `R26_`/`R27_` 开头或含 `RESEARCH`，否则会被当成普通写排进公平队列 | B01-02 报告列出未识别的操作名 |
| L6 关键写名单不动 | `isCriticalBusinessOperationR914` 名单是 CP06 真机修正结果，R30 不增不减 | diff 检查 |
| L7 主线程 | 主线程禁止任何写（CP06 已抛 `CP3_DB_WRITE_ON_MAIN_THREAD`），B02-05 再清读 | StrictMode |

### 4.1 模板A：逐行幂等更新——以 `LiveShadowsR27.settle` 为例（完整替换代码）

已静态确认的问题：`settleBatch` 末尾
`UPDATE r27_opportunity SET settled=(SELECT count(*) …) WHERE target_ordinal<=?`
每次结算都把**全部历史期**重算一遍（r27_opportunity 每期 +1 行，永远增长）。实测（本包 evidence/settle_aggregate_benchmark.json）：2 万期×24 观察者时桌面 CPU 上 49.9ms，只更新本批涉及的 24 个期号仅 0.15ms；手机慢 5–10 倍，已越过 200ms 硬上限且继续线性变长。

替换 `LiveShadowsR27.java` 中 `settle(...)` 与 `settleBatch(...)` 两个方法为（其余方法不动）：

```java
    static final int SETTLE_CHUNK_R30 = 160;

    static long settle(RuntimeR27 rt, ResearchPoolR27.Worker w, long latestOrd) throws Exception {
        long[] settled = new long[1];
        // R30-B01-04: 每片 ≤160 行一个事务；汇总只更新本片涉及的期号。每条 UPDATE 都带 hit IN(-1,-2)，片间幂等。
        for (ResearchWriteQueueR27.Batch chunk : settleChunks(w.ro, latestOrd, settled, SETTLE_CHUNK_R30))
            RuntimeR27.submit(w, "LIVE_SETTLE", chunk);
        return settled[0];
    }

    /** 兼容旧调用与旧测试：把所有片合成一个 Batch（内容与旧版相同，只是汇总语句改为按期号）。 */
    static ResearchWriteQueueR27.Batch settleBatch(SQLiteDatabase ro, long latestOrd, long[] settled) {
        ResearchWriteQueueR27.Batch all = new ResearchWriteQueueR27.Batch();
        for (ResearchWriteQueueR27.Batch chunk : settleChunks(ro, latestOrd, settled, Integer.MAX_VALUE)) all.ops.addAll(chunk.ops);
        return all;
    }

    static List<ResearchWriteQueueR27.Batch> settleChunks(SQLiteDatabase ro, long latestOrd, long[] settled, int perChunk) {
        List<Object[]> rows = new ArrayList<>();
        try (Cursor c = ro.rawQuery(SETTLEABLE, new String[] {String.valueOf(latestOrd)})) {
            while (c.moveToNext()) rows.add(new Object[] {c.getString(0), c.getLong(1), c.getString(2), c.getInt(3), c.getInt(4), c.getInt(5), c.getInt(6), c.getInt(7), c.getString(8), c.getInt(9)});
        }
        List<ResearchWriteQueueR27.Batch> out = new ArrayList<>();
        ResearchWriteQueueR27.Batch b = QualificationInboxR29.pendingDraws(ro, latestOrd); // 缺期记账只放第一片
        java.util.TreeSet<Long> ords = new java.util.TreeSet<>();
        long now = System.currentTimeMillis(); int inChunk = 0;
        for (Object[] r : rows) {
            String id = (String) r[0]; long ord = (Long) r[1]; int actual = (Integer) r[9];
            if (actual < 1) continue; // malformed draw value: never invent an outcome
            boolean frozen = "FROZEN".equals(r[8]);
            boolean hit = frozen && (actual == (Integer) r[4] || actual == (Integer) r[5] || actual == (Integer) r[6]);
            b.add("UPDATE r27_live_frozen SET hit=?,settled_at=? WHERE policy_hash=? AND target_ordinal=? AND hit IN(-1,-2)", hit ? 1 : 0, now, id, ord);
            ords.add(ord); settled[0]++;
            if (++inChunk >= perChunk) { closeSettleChunk(b, ords); out.add(b); b = new ResearchWriteQueueR27.Batch(); ords = new java.util.TreeSet<>(); inChunk = 0; }
        }
        if (inChunk > 0 || !b.isEmpty()) { closeSettleChunk(b, ords); out.add(b); }
        return out;
    }

    private static void closeSettleChunk(ResearchWriteQueueR27.Batch b, java.util.Set<Long> ords) {
        for (Long o : ords)
            b.add("UPDATE r27_opportunity SET settled=(SELECT count(*) FROM r27_live_frozen f WHERE f.target_ordinal=? AND f.hit>=0) WHERE target_ordinal=?", o, o);
    }
```

语义对比：旧语句对“未在本批结算的期”也会重算 settled，但这些期的 r27_live_frozen 没变化，重算结果不变——新旧在最终数据上逐行一致（B01-04 验收要求用同一回放数据集对比 r27_opportunity 全表）。

### 4.2 模板B：保留/清理类 DELETE（RetentionR26、DataRetentionGovernorR900 及以后所有清理）

```java
    /** 把一条可能很大的 DELETE 拆成每事务 ≤500 行；原 WHERE 条件字节不变。 */
    static long deleteInSlicesR30(DbStore store, String operation, String table, String where, Object[] args) {
        String sql = "DELETE FROM " + table + " WHERE rowid IN (SELECT rowid FROM " + table + " WHERE " + where + " LIMIT 500)";
        long total = 0;
        while (true) {
            int n = store.coordinatorForResearchR952().runAtomicWriteOrThrowF01(operation, db -> {
                db.execSQL(sql, args);
                try (android.database.Cursor c = db.rawQuery("SELECT changes()", null)) { return c.moveToFirst() ? c.getInt(0) : 0; }
            });
            total += n;
            if (n < 500) return total;
            if (com.ethk3.novaonepro.RealtimePressureGateR811.hasActiveCriticalWork()) Thread.yield(); // 片间让出
        }
    }
```
WITHOUT ROWID 表把 `rowid` 换成主键列（`TableCopierR30.pkOrder` 同口径）。
