## 2. 为什么这次能施工（与 R29 的区别）

| 项 | R29 B01 | R30 B11 |
|---|---|---|
| 迁移范围 | 378 张表（Root 研究域+旧域） | 仅 r27_* 共 32 张（除 r27_fetch_reject、r27_chart_cache） |
| 写者数 | bb607cf 106 个文件 1890 处（R29 后 124 个文件）、线程局部路由 | 13 个文件 66 处（附表B），R27 引擎主写入口只有 ResearchWriteQueueR27 一个 |
| 复制方式 | 边写边复制 + 追平 + 哈希漂移检测 | 进程启动时、研究 worker 启动前一次性复制，期间无研究写者 |
| 漏网写者 | 事后发现 `ROOT_RESEARCH_ADVANCED_AFTER_SEAL` | 冻结触发器：第一次写就 `RAISE(ABORT,'R30_RESEARCH_TABLE_FROZEN:<表>')` 带表名 |
| ATTACH | 不用 | 不用（Android 对 ATTACH 会关闭 WAL） |
| 校验 | 自定义 typed row chain | 行数 + 按 rowid/主键顺序的内容 SHA-256（OfflineCutoverR30.ContentHash）+ integrity_check |

SQL 合同 T03（冻结触发器三种写全拦截、state=2 后 Root 永久只读、state=0 恢复）与 T06（rowid/WITHOUT ROWID 分页复制、幂等重做、缺列上报、内容哈希一致）已在本包实测通过。

## 3. 路由点

切库后 r27_* 的读写只能通过：`ResearchWriteQueueR27`（批量写，唯一 writer 连接）与 `StoreR27`（读连接与少量直接写）。附表B 中其他文件的直接写点逐一改为调用 StoreR27 研究连接；改完后再跑 `scan_table_writers.py --prefix r27_`，结果中只能剩 ResearchWriteQueueR27/StoreR27/SchemaR27。
