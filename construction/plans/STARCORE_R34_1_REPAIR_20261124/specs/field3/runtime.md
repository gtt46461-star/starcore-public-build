## 本次新增的源码证据与施工边界

- **B05，UI 展示依赖进入抓取线程。** 新线程栈实际采到 `eth_k3_fetch_channel → runFetchChannelOnce → handleLatestDrawAfterSave → postAnalysisForLatest → broadcastSettlementUpdated → broadcastSimpleStateLimited → DbStore.getRuntimeState → SQLite`。122 源码在广播前还读 latestDraw，并在强制广播时绕过显示节流。单次栈没有该调用累计时长。用独立阻塞注入及 UI 打开/关闭对照测原因，从抓取线程移开展示读，保留原事实和服务通知。
- **B05，持久返回观察会在缓冲区满时消失。** `IssueTimelineWriterR30.committedAt` 超过 256 后递增遗漏并返回。将 drain 的实际执行、耗时、最早等待和原始回读加入服务层取证。迟到写入只允许保留当时已观测的时点。发生进程死亡，无法证明的返回只记未测。B05 工程用例也覆盖 UI 不可见、研究未注册及写者受限场景。
- **B04/B11，修好当前状态卡不等于逐期覆盖。** 用 603 与 604 的独立角色对照锁定缺冻结问题。另有 R923 汇总显示预测结算 1,259/1,188。源码 `RuntimeTruthSnapshotR906.coverage/coverageSnapshotCP4` 的 eligible 要求热表 draws 中有 clean 行；settled 却查历史 strict_oos 标签存在，不要求属于同一批热表开奖。两者范围可随 5,000 期滚动分离。在线异常还会构造全零结果，`SettlementCoverageTruthR906` 在分母为零时可给 0.0。以同一快照、窗口、游戏及 role 的 eligible 作为两者母集，缺行、未结算、已结算与历史保留分别标记；对 >100% 的矛盾留原因和证据。禁止压平或删除历史行以修饰结果。
- **B04/B10，持续运行须同时看到进出流量。** 将本次积压净增和实际快照规模加入第 2 版同一工单，保留迁移、重试、限额及回滚约束。导出、维护或坏对象不能把赛前出号和已冻结任务结算一起阻断；恢复与追赶也不能制造事前冻结。
- **无人干预取证。** 预先固定全部目标与关闭界面的时刻；分别记录用户手动恢复、页面打开、OS恢复和诊断启动。对页面重开前后按原事件时点和生产来源归属，重开后补处理的结算可以记真实结算及延迟；超过开奖截止的补算绝不可计赛前覆盖。异常出现后继续保留缺期，检查同一安装在真实后台连续 72 小时的 24 小时截面和完整窗；研究采样跨这些时段也须给出各阶段真正提交和消费的产物。
