# 每期业务和连续两代研究的联调验收

## 现场先回答哪三个问题

1. **关掉界面后哪些期真正完成了业务？** 在服务启动前预登记目标日历，用 draw、赛前冻结及权威结算原件逐键左连接。对没有业务原件的期保留缺口。区分基础影子、候选影子、主链 NO_BET 和合法 REAL。每期给出发起者、进程与 boot、权威时间及可比性。恢复后补处理的历史保留实际提交时间。由 B04/B05 测服务引发的工作，由 B11 出对账表。
2. **哪条公式从上一次结算学到了东西？** B06–B08 在同一个研究运行中逐项串联候选、训练输入、优化器更新、发布、赛前消费、标签、结算、反馈、研究产物和下一代来源。每个已开奖期都应在训练机会账上出现，正常有输入时推进合法工作。无标签、错角色、断档、排队等待分别记录影响对象、开始时间、最老待办和下一次恢复条件。重启继续原游标；持续无进度归为失败或待处理。实时冻结使用已就绪的发布版本。把研究重计算分片安排在赛前关键路径之外。
3. **没有产生合格策略时，研发还会继续吗？** B12 安装受控数据后，从生产服务入口跑两轮。第一轮结算引发新研究，消费落到一个不同结构的变异后代。第二轮让该后代与另一条有完整来源的父代按同目标输入融合，再使融合子代完成后续发布、冻结和结算。台账需能回答两代分别改变了什么、哪些改变无效、下一轮如何分配计算。夹具只驱动受控输入及应当触发的条件；用相同生产调度、写入、恢复和消费者。自然观察无需每期都发生变异或融合，事件触发后才评其成效。

## B12 的可执行证据格式

`tools/verify_learning_trace.py` 是对**隔离工程场景**的离线验收参考实现。施工时由既有计划中的 `tools/r341/verify_integrated_chain.py` 驱动生产入口，导出带身份的 JSON 索引及证据目录，再调用此工具。不要求向实时库写一套平行事件。优先引用现有 receipt、SQLite 已提交行、不可变产物与测试驱动记录。每条引用的相对路径指向一个规范化 JSON 记录，可以从完整原件按键提取；保留提取器版本、原始输入和原始日志供复验。

索引字段为 `scope=ENGINEERING_FIXTURE`、`run_id`、`source_commit`、`apk_sha256`、`time_scope`、`cycles`、`births`；后两者是按因果顺序排列的相对路径与 SHA-256 对象。每代保留 train、publish、freeze、settle、feedback、research 六种实际记录，再提交 birth。各记录带相同运行身份、role、stage 及该阶段引用的上游文件摘要。采集器须先验证 Android 的生产回执，再投影对应字段。这个小工具核对数据联结、时序、状态及应用两代的来源；它不会连接手机或读出生产数据。

三代固定在同一可比较时间域。索引及各阶段 JSON 原件带同一 `time_scope`（设备、boot、单调时钟及单位），由采集器在此域记录实际提交/观察时刻；权威 deadline、开奖时间的换算须保留锚点。每轮依次校验 train 的 `started_at/committed_at`、publish 的 `published_at`、freeze 的 `returned_at/deadline_at`、settle 的 `draw_at/settled_at`、feedback 的 `committed_at` 和 research 的 `completed_at`。冻结须严格早于截止。时钟刻度相同的有序提交由阶段摘要引用定序。出生的 `committed_at` 位于上轮研究完成与子代训练启动之间。首代 train 明确提交 `birth_ref=null`，后代必须提交上一条出生原件的 SHA-256；其 `formula_original` 与出生时 `child_original` 必须指向相同内容。再做亲代时，该公式的原件也须一致。

正例输入预置三组会得到不同数值模型的可区分训练用例。训练的 `state_original.weights_original` 提交相对路径、摘要及可复算的规范化数值权重字节，只包含固定顺序、固定编码的实际参数，排除 ID、封装、时钟及优化器元数据。在发布端和冻结计算实际载入参数后分别导出 `weights_sha256` 与应用原有的 `model_hash` 一起核对。验收器读取权重字节重算，只有三轮各自的新权重确实发布、消费才通过此受控正例。自然运行可出现收敛或参数不变，其证据仍按生产合同记录。

- 受控正例至少含三个依次消费的公式身份、两次连续出生（先变异，再融合），第三个融合子代也实训、发布、冻结、结算。三轮均保留数值优化前后摘要、相应样本数、模型消费、目标位置和三号码、对应开奖排列。同一运行内只用隔离的开发/影子样本。
- 研发负责人须另附规范化 AST、探针输入与行为向量、模型和优化器原始状态、两个父代以及消融原件，完成 B06–B08 的原场景检测。报告须说明为何发生变化，以及是否改善开发验证。任何结构或质量结果不足时按实际终态记录。
- 负例至少覆盖拿另一目标的结算贴到本期、将同一模型冒充新训练、父代重名充融合、反馈消费两次、用 FUTURE 标签训练原模型、将事后冻结移入赛前、错误期望命中、只有一次出生、子代预测早于父代结算、跨时钟拼接、错拿出生或换用同策略 ID 的另一份程序，以及三套标签指向同一份旧权重。对漏一期的自然场景仍以 B04/B05 的完整日历判别，本工具的三轮受控例只验跨代连通。
- 运行失败时定位具体环节与缺少原件。两代联调之后仍要用同一 APK 的无人干预真机水位验证持续运行。工程例的命中率、子代数量或测试工时都不转成独立未来资格。

## B12 正式回执入口

在第 3 版工程用例 `A-B12-03b` 的 `execution_artifact` 设置 `learning_trace_index_artifact`，其值为相对本批回执证据根目录的索引文件名，例如 `trace/index.json`。索引的 `source_commit` 须与回执的 `source_after` 一致。索引内全部阶段引用、公式、数值权重等深层原件均相对索引所在目录解析。批回执的 `artifacts` 按证据根目录逐项申报并保存其 SHA-256，例如 `trace/weights1`。遗漏任何实际消费的原件，整张 B12 工程通过回执会被拒绝。

复用批回执的 `apk_artifact`、`apk_identity_member` 和 `apk_sha256`。工程回执未声明 APK 或模板中的字段仍为 null 时，在本用例的 `execution_artifact` 写 `apk_artifact` 和 `apk_identity_member`，并将实际 APK 文件列入 `artifacts`。验收从实际文件重算 SHA-256，对比索引及已申报的 APK 摘要，解出唯一构建身份资产核对施工提交与方案封印。若两处都声明同一字段，取值须一致。

从方案目录运行。首条命令可单独排查三代原件；第二条是工程签收，复核源码、运行记录、APK、申报清单及三代链。

```bash
python3 -B tools/verify_learning_trace.py --index "$evidence_root/trace/index.json" --evidence-root "$evidence_root/trace"
python3 -B tools/verify_receipt.py --plan . --receipt "$receipt" --evidence-root "$evidence_root" --repo "$app_repo" --level ENGINEERING
```
