# 工程测试实际进入 Android 用例以及新文件的首次创建

固定 122 应用的 `app/build.gradle` 在 `r30Instrumentation=true` 时选择 `com.ethk3.novaonepro.R30FaultAndroidRunner`。其 `newApplication` 安装 RoutedContext；`onCreate` 在 `super.onCreate` 之前要求显式 `r30Sandbox`，原正则为 `[A-Za-z0-9_-]{1,80}`。未安装该 context 会得到 `application context not installed`，未提供或不合法的值会得到 `explicit r30Sandbox required`。绑定的 `gradle.properties` 和 Android defaultConfig 均未提供默认值。第 4 版 B01 至 B11 的 134 个 Gradle 工程命令全部漏传，手工在 argv 后追加也会被旧回执的精确校验拒收。源码定位为 `R30FaultAndroidRunner.java`（Git blob `63a4811bd1b21423650e5bc0eb3e241e54b3636e`）及 `app/build.gradle`（`bff4ae42c5bc451a0a33775dc0ab5a0d6964e885`）。

## 开工与采集

1. 工程场景使用独立测试设备或模拟器、实际 debug 目标 APK 与配对的测试 APK。当前包名为 `com.starcore.research.r13`，namespace 为 `com.ethk3.novaonepro`。先核对 AndroidJUnitRunner 组件、合并的 test manifest 及实际目标包。B01 原构建与签名依赖仍按原计划读取；测试产物和用户设备上的 release APK 各自记录身份。一次指定一台设备；多台并行时分别保存每台原件。
2. `tools/dispatch5.py --plan "$p" --case R341-B01-02-T01` 会打印 JSON argv，含 `:app:connectedDebugAndroidTest`、`-Pr30Instrumentation=true`、准确的 class#method 和本次专有的 `-Pandroid.testInstrumentationRunnerArguments.r30Sandbox=r341_<case>_<32位随机小写十六进制>`。命令中的 case 将连字符替换为下划线。可由 Python 的 `subprocess.run(argv, cwd=应用工作树)` 执行；保留该次实际 argv。新的运行或整例重试换令牌；同一场景内部复投、事务恢复在该例同一数据范围内进行。工程图表和资格输入同样隔离。
3. 实际 runner 初始调用 `setUserEnabled(false)`。需要用户启用服务的正例在本例隔离的上下文通过生产设置/服务入口启用并记录第一笔业务提交；关停和 force-stop 反例保留关闭语义。单进程默认使用 noBackupFilesDir 下的 `r30-instrumentation/<scope>/<applicationId>`；实际传递的缓存、文件与数据库读取同一路由。需模拟进程死亡且保持真实共用应用数据、包括跨 `:diagnostics` 服务时，按 122 已有 `tools/r31/run_r31q_android_delivery.sh` 的模式在干净可丢弃模拟器中显式 `r31qRealService=true`，取回 `ro.kernel.qemu=1` 及预先建立的隔离镜像依据。源码提交的等价映射明确选择该项。避免在用户已有数据设备上执行共同根的工程场景。DEVICE 测试仍用真实安装包和原后台观测协议。
4. 在批次已有的 Android 测试方法进入处、所有业务断言通过处，通过 `InstrumentationRegistry.getInstrumentation()` 读取实际 `arguments` 与目标 Context 的 dataDir；同时从运行包和类读取真实包名、runner、测试类/方法和构建源提交。向该设备 logcat 各写一次单行 `R341_INSTRUMENTATION {JSON}`，保存原始设备日志和本次 AGP 的逐设备 native JUnit XML。JSON 中的 `event` 分别为 `CASE_ENTER`、`CASE_ASSERTIONS_COMPLETE`，带下述身份以及实际 dataDir。通过 elapsed-time/logcat 过滤同次采集，保留完整原件；之前运行的相同方法的 XML 不能单独证明当次执行。
5. 执行原件加 `instrumentation_artifact` 指向汇集记录，所有引用进 `artifacts`。记录包含 `case_id,source_commit,variant=debug,package,runner,selected_class,selected_method,r30Sandbox,r31qRealService,target_data_dir,device_serial,junit_xml_artifact,junit_xml_sha256,device_log_artifact,device_log_sha256`。共同数据根另含 `disposable_emulator=true,qemu_property="1"`。若使用已提交的等价运行映射，仍要保留同一 method selector、唯一 scope 动态槽；Gradle 的参数形式和 adb 的 `-e r30Sandbox <R341_SCOPE>` 均会核对实际参数。本合同默认的 debug 构建及 JUnit 原始结果保持有效；采用 adb 驱动时同时取同次 instrumentation 的实际 JUnit XML 原件（或使用 Gradle 驱动的等价测试）。
6. 同批首个使用的新文件负责创建。此后工单仅向同一文件补充自己的方法及回归；保留前面的方法和源码。第 4 版 13 个文件有 50 处后续 NEW，其中 12 个是共享测试套件，另一个是 `QualityExperimentR341.java` 在 B09-03 初建、B09-05 再扩充工厂诊断。第 5 版逐处校正；旧库来源追溯中的 `issue_ids` 并非物理创建顺序。工作树实际顺序来自 WORK_ORDERS 及 FILE_CARDS.changes_in_order；程序复查用例的 runner 与有效文件最迟在本工单就绪。

## B05 真正杀死主进程时，谁记录结果

`R341-B05-01-T02` 和 `R341-B05-03-T01` 另需 `process_transition_artifact`。由外部主机/模拟器控制器从目标 APK 的正常服务入口执行持久工作、进程退出、恢复和业务提交，主机持续采集，不把控制器放在要杀死的主进程中。交付本批 JUnit 前先完成该段并将原件保存到主机。最后才启动已登记的 JUnit 方法验证这些只读原件以及本例其余断言。重新安装、启动 instrumentation 或其 onCreate 关闭用户开关均不能计作先前生产服务的自恢复。对 force-stop 阴性场景单列用户明确重新启用边界，不要求系统在用户强停期间自行恢复。该合同核查进程终止、同一次设备 boot；需要跨整机重启的独立场景另按 boot 边界取证。

1. 先生成该用例唯一 scope，向同一可丢弃设备安装已构建的 debug 目标 APK，读回设备 serial、包名、安装 APK 字节及 SHA、boot ID 和可比单调时钟；给本次隔离数据库登记稳定身份及唯一待办业务键。用本批测试夹具设置用户启用、加入输入，然后从目标服务正常入口启动。区分宿主与实际目标进程。服务创建持久待办后，由宿主记录 `/proc/<pid>/stat` 的启动 tick 和实际提交状态。以受控进程死亡模拟系统回收；保持真实业务库、用户设置及设备镜像。校验旧 PID+启动 tick 已退出；恢复后核实新的主进程、启动来源与同一业务键的唯一实际提交。使用宿主观察 Activity 启动和进程变化的连续原始 adb/系统日志、实际 SQLite 提交原件作证。
2. 该段不依赖 `R30FaultAndroidRunner` 存活，也不以 instrumentation 开始复查时能创建 Activity/服务代表业务自行恢复。默认私有根的 JUnit 可核验已导出的只读原件；如果 JUnit 必须直接读取生产共同数据库，使用第3步的同一已登记等价映射、可丢弃模拟器和 `r31qRealService=true`。运行前分配的 scope、设备和两段采集一致。最终把阶段原件和 JUnit/设备日志一并列入工程回执。普通测试命令的成功本身不满足这两个用例。
3. 索引格式为 `schema=R341_HOST_RESTART_1,case_id,package,source_commit,r30Sandbox,device_serial,boot_id,observer_session,db_identity,work_key,installed_apk_sha256,installed_apk_artifact,disposable_emulator=true,qemu_property="1",event_artifacts`。四个独立事件带索引身份、`observer=EXTERNAL_HOST,kind,elapsed_ms,activity_starts_since_start`，顺序为 `WAITING_COMMITTED,TARGET_EXITED,SERVICE_RESTARTED,WORK_COMMITTED`。第1、3、4条记录目标主进程的 `process_name,pid,start_ticks`。退出事件记录 `retired_pid,retired_start_ticks,old_process_present=false`；恢复事件记录实际 `launcher`。待办与恢复事件记录累计已完成笔数 `committed_work_count`；末笔同时记录 `commit_origin,pending_count_for_key,business_result_artifact,business_result_sha256`，所指真实业务提交按同库、同业务键、同新进程及次数复核。外部观察与设备原始数据的生成方式须留在实际工程执行原件中。

索引另记 `apk_identity_member`，用于在实际安装 APK 的 assets 内匹配同次回执的 sourceCommit 和 planSha256。上述两例的最终 JUnit `CASE_ENTER` 原始设备事件还须附 `boot_id,installed_apk_sha256,elapsed_ms`，复算必须发生在外部最后一个业务提交之后，同设备、同 boot、同一个已安装 APK。
