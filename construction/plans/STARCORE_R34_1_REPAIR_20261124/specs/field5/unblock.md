# 从写入拥塞到第一条 R27 策略和首次重放

两份 122 报告的 `DIAGNOSTIC_SCOPE.json/tables` 均已登记 3 条 `r27_replay_dataset` 表头、1 条 `r27_evolution_cursor`。策略、谱系、重放评分、完成代和在线影子均为 0。两份 `R26_REPORT.json` 的 `sectionId=CONTINUOUS_RUNTIME` 里，`r27-replay-dataset` 的 cursor 为 3597847、steps 为 3，`r27-evolution` 的 cursor 为 13、steps 为 4，两次均停在原值。新报告依次记为 `WRITER_HOLD_FAULT_BACKLOG` 和 `DEPENDENCY(r27-replay-dataset)`。表头计数不能证明关联的 pin 原件完整、有效，也不能证明进程已把该输入交给进化工人。先按任务行、目标、输入 hash 和提交键找首个缺失环节。

## 两个有机会的研究作业争同一写者（B02）

122 的 `DatabaseCoordinator.researchDataDueR335` 读取全局上次研究数据服务时间和实时冻结等待数。`runWrite` 对研究数据共用一个预约位。`RuntimeR27.DatasetTask.step` 在检查已提交输入之前就判断此全局状态。确定性反例可保持故障背压达到 24、没有临近冻结，在每个已到期的服务窗口，让另一个合法研究数据任务先取得预约、成功提交；隔 1 ms 运行 dataset。后者每次读到刚更新的全局时刻，连续多次返回等待。研究 lane 有真实提交时，某一个生产依赖仍可能永远没有服务。报告只证明等待关系，没有逐次服务顺序，复现条件不能直接定为现场唯一根因。

让已就绪的最老工作键在执行 `DatasetTask.step` 的轻量准入环节即可进入已有 writer 的同类排队。保存任务、输入身份、就绪年龄、在本次机会中的选择和提交/续排结果，防止其他任务的提交重置这项工作的年龄。保留原实时截止、故障排水和单 writer。B02 可使用两种已就绪的研究微批、虚拟时钟和当前生产调度入口独立验收；在预登记有容量的窗口，两者各有服务，回滚和作废输入不计生产进度。真正被实时冻结占满时按原合同计入饱和段，不能承诺无条件排水。

## 已经落库的输入，重启后能否直接重新取得（B08）

`RuntimeR27.DatasetTask.step` 有按已保存的游标 hash 和按重新装载的数据 hash 两种恢复路径。`publishRecoveredReplayKnowledgeR31` 即使 `ReplayKnowledgeStoreR31.isPublishedR31` 对同范围、同原始时间和 payload 已返回真，仍会执行 `submit(REPLAY_KNOWLEDGE_RECOVERY)`；恢复模式进入 payload，刚发布的新输入与其恢复模式亦可能有不同 payload。该投影写在 `r27_chart_cache` 的固定键，属于输入出处说明。并发、驱逐或故障可能使它缺失，不能用它单独判断数据集有效。

在既有输入所有者内区分**读取已提交且一致的恢复证据**和**确需修复一项投影**。前者用有界的恢复工作，在一个可比数据库视图核对出生游标的 dataset hash、表头、分段、实际 pin 原件内容、来源修订和失效记录，重新确认当前任务 owner/fence。已有同身份恢复投影的立即读回，按原规则向进化工人交付；该路径不要求另取写槽。若产品合同要求把 NEW 发布改记为 RECOVERED，按不同业务事实显式补写；不能伪签不同模式或把表头当 pin。投影缺失、被替换或待更新时沿原持久化协议有界恢复，使用目标投影/原 pin 的稳定身份重试，防止无关任务的新 commit 造成无限重建。遇到真失效、取消或换 owner 时保全旧谱系、禁止发布。切片时限、堆与读预算仍要执行；缺原件时走有据重建，独立的已验证输入应能推进。

正例以真实 pin、已存在且匹配的恢复投影和正确游标打开新进程，阻挡该项冗余的投影写，读取仍能发布对应输入；核对下一进化切片实际使用相同 hash。另一组移除投影后释放写槽，确保只恢复一次，崩溃/重投得到相同结果。分别只留三条表头、调换 pin 或 fence、错带修订，必须报告首个错误并拒绝消费。本批接 B06 的已有合法测试输入再验证 BORN 和首个已提交重放结果。缺少样本支持的窗口记录具体阶段。

## 坏的历史确认包不能挡住无关公式的首个出生（B06）

`FrozenConfirmationStoreR30.nextPending` 按 `created_at,task_key` 永远先取最老的 PENDING 单行，仅取 `packet_json`，随后立即 parse。`RuntimeR27.EvolutionTask.step` 在每个步骤调用 `loop.step()` 前都先取该行。恢复入口 `confirmFrozen` 的异常处理晚于取包。一条更老、不可解析的确认包足以使无关工厂每次重试都在评估新公式前退出。若表行 A 的正文实际归属另一任务 B，`nextPending` 亦未在此读取路径比较两者。两个现场快照的 `r30_frozen_confirm` 都为 0，这一分支属于产品升级和历史数据恢复回归。

把稳定行键、原字节/摘要、状态和选择顺序一起读回。对确定性的单行内容损坏，按行键和原摘要作可重入的隔离标记；原件及原有曝光/消耗事实继续保存。每片处理有上限，下一次选择有机会到达无关的合法包，独立公式的进化切片也必须继续。当前代明示依赖损坏确认时保留为缺证，禁止再看相同确认结果、宣布通过、登记未来或获证。锁、取消、提交状态未知、数据库损坏与单行内容无效分流；提交未确定时先回读，不批量跳过。B06 夹具预置 B08 之前已能读的有效输入，在同一库给最老坏行、下一合法行以及允许出生的公式，核对真实 BORN、对应谱系和首个开发重放；再验证一次重启不会再次结算确认或重复出生。B08/B09 后续仍复验原有确认、登记和资格规则。
