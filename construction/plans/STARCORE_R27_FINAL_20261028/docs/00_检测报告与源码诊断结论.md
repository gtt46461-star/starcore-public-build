ABI 变化（`ResearchSemanticsGeneratedR967.TRAINING_RULE_SHA256`）是源码哈希派生的。每次装新版，它就变，下面三处就会把已学到的东西"冻结保护"然后不再前进：

1. `strategyv2/LegacyReplayR26.java:40` 与 `:99`：`if(!abi.equals(r.abi)) preserveBlocked(...,"BLOCKED_NUMERICAL_ABI_PRESERVED"); return 0;` —— 旧学习核从此永远返回0。
2. `ResearchPruningR965` 的淘汰合约以源码树哈希为键（`r965_research_pruning_<sourceHash>_<algo>`），新哈希 `93a33a8a…` 下全部算法 n 重新从 1、3 开始（旧哈希 `f7cc5da2…` 下已攒到 n=13—22，作废）。
3. R26 的4个冻结策略 `runtimeStatus=BLOCKED_NUMERICAL_ABI_PRESERVED`。

**这就是"随便看一个算法半天才跑了二十期"的第一根因：每次升级把样本计数清零，而且清零后的新计数又被下面的饥饿问题拖慢。** → R27-B02（证据连续性）。

## 0.3 研究线程被饥饿（实时跑不起来）

源码 `strategyv2/RuntimeCoordinatorR26.java`：

- 所有47个研究任务（31个系统任务＋16个专家）只有 **一个线程** `starcore-r26-continuous-research`，优先级 `THREAD_PRIORITY_BACKGROUND`，按 `SLOTS={"P1","P2","P2","P3"}` 轮转。
- 主循环第99行：`if(preempt()){sessionBlocked("CRITICAL_DEADLINE");await(50);continue;}`。`preempt()` 只要 `SettlementExecutionGateR819.isActive()` 或 `RealtimePressureGateR811.hasActiveCriticalWork()`（分析深度>0或结算深度>0）就为真。开奖是 **每60秒一期**（报告 `e92f1b…` 中 open_time 每期差60000ms），抓取→落库→结算→冻结在一分钟里占用相当比例，研究线程整段让出。报告 `runtime-observation.json` 当时 `realtimePressure=true`。
- 每个切片预算 `BudgetTokenSU1(200,…)`，并行计算用 `CooperativeContinuationR26.slice(150)`；单片超过1000ms即记 `CAPACITY_FAIL:UNSLICED_KERNEL`（累计119次）。
- 结果：会话CPU只占单核3.8%，`serviceWallMs=365,610`（约6分钟）/ 会话约97分钟。

**这是"实时跑数据太慢"的第二根因。** 并非手机算不动：第1章实测，一个线性候选在5000期上做完整逐期前推只需几毫秒。→ R27-B01（运行主干重构）。

## 0.7 校准一行迟到就整批作废，导致证书永远为0

`CandidateCalibrationR932.java:276-277`：241个固定观测里，任何一行 `fetch_time>=openTime` 抛 `R77_CAL_STRICT_TIME_REJECTED`；任何一行不等于"下一个评价期"抛 `R969_CAL_EVALUATION_SCHEDULE_GAP`。一抛异常，整个研究标 `BLOCKED_INVALID_INPUT`、预约置 `FAILED_GAP`，从头再攒241期。报告：`calibration_ready=0`、`calibration_fitted=0`、`formal_windows=0`、`active_gate_passing_certificates=0`、`exact_real_consumptions=0`；12条阻塞记录全部是这两个原因。

**"证书0、主链0"的直接原因不是"门槛太严"，而是"证据链在数据层就断了，根本没有走到门槛面前"。** → R27-B07。

## 0.9 深度学习误差曲线为什么大起大落

图表 `ChartsRepositoryR83.networkBrier()`（第279—300行）：

- 数据只取 `AtomicToolWorldR943.CONTEXT` 里最近 ≤139 行已结算样本，实际只有 **88** 个；
- 滚动窗口只有 **20** 期；对照线写死 0.21；
- 网络（7组原子特征→16→8→1）**每期只用一个样本做一次SGD**（`AtomicToolWorldR943.java:139 network.network.update(groupFeatures(values),hit)`），没有历史预训练、没有小批量、没有学习率衰减；
- 样本来源依赖 lane0 赛前冻结上下文（`hit=-1` 的行），冻结赶不上截止就没有新样本 → **0669后完全停更**，所以曲线最后一个点是0669。

统计事实（第1章工具 E 项实测）：一个完全没有预测能力、概率在0.3附近抖动的模型，88个样本上滚动20期 Brier 的典型区间是 **0.147—0.289**，5%/95%分位 **0.108—0.349**。截图中 0.078—0.275 的曲线，基本落在纯噪声区间内；那段"下降到0.078"不是学会了，而是刚好碰上一串未命中且模型给了低概率。**滚动20期 Brier 本身就不能用来判断"越学越准"。** → R27-B06。

## 0.11 胜率现状（报告能给出的全部事实）

- 旧系统43个算法：18个 0 样本；其余样本量 1—32 期，例如 11/20、11/19、13/32、10/30、10/28、2/7。
- 主链：每期 `PRODUCTION_FALLBACK|NO_VALID_CERTIFICATE`，`applied=0, weight=0.0`。
- R26 4个策略：`acts=0`。
- 报告自身声明：`NO_GUARANTEE_OF_HIGH_HIT_RATE_OR_MONOTONIC_EVOLUTION`。

第01章用仓库自带的1万期历史数据把"这些数字意味着什么"讲清楚：43个算法各跑20期，在 **完全没有优势** 的情况下，最好那个的命中率中位数就是 **55%**；跑到120期，这个"运气最好值"才降到39%。所以界面上看到的55%、58%不能作为"高胜率"的证据。

## 0.12 R26 方案本身的缺陷（R27 修正）
