# 为什么体积变化，以及本版如何完整保留

|包|实际字节|十进制MB|主要区别|
|---|---:|---:|---|
|原10.25|41,461,432|41.46|原始完整方案、代码与证据|
|R21完整|98,366,245|98.37|包含原10.25原包和三个较大模型检查点|
|R22完整证据|13,418,559|13.42|包含检测报告及R21轻量版，没有原40MB包与全部大检查点|

R22的设计要求是累计的，但文件随包程度与R21完整不同；此前不能把“功能要求保留”说成“所有原始文件都装进13MB里”。R23提供单个完整总包，原样装入R21完整与R22完整。原10.25原包在R21内部，其hash与用户上传一致，已实际离线展开核验。

原10.25 CRC与SHA通过，原检测报告CRC与SHA通过。展开得到原10.25的635项归档成员、R21的156项、R22的72项；这些数字是归档条目数，不是算法家族或代码实现数量。工具拒绝路径穿越并已测试。

`prior_text/`有可直接检索的旧方案正文，`registries/requirements_P001_P124.csv`有124项统一需求。无需仅凭“嵌套压缩包已存在”猜测保留完整；核验工具会验证两个外包和嵌套原包的SHA。

文件大小只说明材料体积，不证明软件能力；本次没有填充无用文件把包做大。模型权重、原始方案和真实预测日志是体积的主要来源。最终能力仍按逐项产物和实盘质量验收。
