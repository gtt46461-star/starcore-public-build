# 唯一主链、所有权与数据合同

## 1. 施工基线

本方案 R34.2 以报告所绑定的 **577311152 / eb8f82a8bda8db22f1f122095217132f07053bcb** 为应用基线。旧 R34.1 第6版 122底座的要求继续有效，旧整文件后态不得覆盖152源码。计划版本、源码提交、安装版本、运行会话、数据库身份、快照身份是六个不同字段。

## 2. 当前实际入口与应保留的顺序

当前服务入口是 `AutoFetchService`，业务协调为 `BusinessReconcilerR36.reconcile`，预测唯一并发所有者为 `AnalysisSingleFlightR36`，计算/提交为 `V51RuntimeOrchestrator.runR36`。`BusinessReconcilerR36` 现有逻辑先尝试下期持久请求，再交接当前开奖结算，目的是不让历史补偿或统计写入推迟下一期预测。保留这一时效设计；不得恢复为“全部历史结算、全部训练结束后才能预测下一期”。

逻辑上的唯一闭环是：合法开奖与历史 → 精确目标期和事前数据快照 → 使用已经发布且兼容的模型计算 → 唯一决策门与事前冻结 → 精确开奖结算 → 结果事件投递 → 训练、反馈、研究、创造/变异/融合 → 独立验证、合格发布 → 后续期读取新模型。

“唯一主链”指每个事实只有一个权威写入者、每个事件有确定的上下游关系。它不是让网络、推理、训练、图表和报告都挤进一个长事务或一个线程。

## 4. 实时通道与研究通道的交点

实时通道只能读取已提交、已验证、身份兼容的不可变模型快照；它不等待新模型训练。若当前没有合格新策略，继续使用原有合法SHADOW基线及其准确状态。研究通道必须持续消费每期已提交结果，但在计算资源不足时以持久游标分片完成，不以“本期维护看过了”代替完成数值训练。

研究发布原子切换一个版本指针。分析请求在捕获时固定该指针；推理中即使发布新版本也不更改当期模型。变异、融合或数值更新之后的新版本重新开始相应冻结评价，不能继承旧版证书和未来样本。

开奖到达后，按其对应冻结记录结算，并在结算提交或持久outbox中记录待投递事件。`outbox事件存在`、`消费者接收`、`真实权重变化`、`新产物可恢复`、`未来效果提高`分别验收。仅有最终游标不能代表前面每个阶段成功。

## 5. 写入、并发与恢复合同

沿用 `DatabaseCoordinator` 单写协调。修复fault backlog闭锁时，保留故障原件、写入预算、保护守卫以及独立排空线程。不可删除保护判断、把所有RESEARCH_DATA提升到REALTIME、把所有失败吞掉后返回成功，或清空故障队列以恢复绿色状态。

现有 `WriterHoldFaultsR31.drainControlSliceR32` 已由独立控制线程执行，单批最多4条且绑定字节受64KB预算限制，只有持久化及回读确认后才出队；本轮修复这条既有通道。当前报告的writer队列观察来自诊断PID 22528，`pending=0 / IDLE / NOT_RUN`；runtime现场PID为18685。两者不能互相替代，恢复验收必须取得主运行PID及processEpoch匹配的排空状态、实际收据与失败原件。

处理顺序：先让排空所必需的最小schema/原件路径可用；对fault drain保留有界服务时隙；原件持久化并回读确认后原子推进排空游标；对依赖失败分类和定时重试；对资产级损坏隔离该资产；仅对确证进程级不变量破坏保持进程级停止。原件无法取得时，该资产保持BLOCKED，不能因此假造可恢复状态。

本次研究启动的4次 `CHECKPOINT_PREPARE` 均为 `VERIFIED`，失败发生在后续 `CHECKPOINT_PRESERVE`。报告另有556个checkpoint原件缺失，这是独立的引用闭包问题，不能据此断言保存事务失败就是这些缺原件造成；先取得该事务的类型化内部原因、phase和commitOutcome并复现，再修具体保存/迁移路径。

三次相同BUG的断路器必须保留其防止热循环的作用，但采用完整类型化原因、依赖版本/修复代、冷却时钟和恢复探针。DEPENDENCY、CAPACITY、资源退避不得误归永久BUG。依赖恢复后，原owner在有界试运行中重新进入启动流程；不靠打开Activity重置计数。

每个生产变更必须写清 owner、线程、数据库、事务、唯一键、lease/fence、deadline、输入输出、重试分类、取消、重启恢复和失败终态。跨库时使用outbox/inbox与水位对账，不持A库写锁等待B库锁。不为本轮修复强制大规模分库；是否迁移由同一文件卡及实际收益证据决定。

## 6. 历史、实时、确认和未来数据的角色

历史滚动数据上限仍为5000期。历史快速训练、开发选择、独立确认和自然未来四种角色必须显式登记；不可把重复回放的5000期变成无限个独立未来样本。相同期的多策略、多位置、1200动作行也不是1200个独立开奖。

历史快训以有序、连续区间为单位生成manifest：范围、缺口、数据哈希、特征ABI、标签规则、角色、cutoff、训练器与初始状态哈希。一次拉取后批量构建特征、分片续训，避免每个候选反复从3GB数据库完整扫描。缺口既不能补造，也不应让所有互不依赖的连续区间和策略永久停工。需要更长跨度的证据仅保留模型/冻结原件和必要依赖，不扩大draws热表上限。

用于当前预测的最小连续历史已有 `DbStore.savePredrawSuffixR32`：通过 `R32_PREDRAW_SUFFIX / DRAW_INGEST` 写入；普通历史批次则为 `R914_DRAW_HISTORY_BATCH / RESEARCH_DATA`。修复必须沿现有最小suffix通道检查调用、目标变化、冲突校验、返回0原因、写入收据和完成唤醒，不另建通道。普通历史批次受背压拒绝，不能直接当作最小suffix也被同一研究背压拒绝的证据。

## 7. 不能用相互冲突的指标签收

当前用户目标保留：抓取目标1s/次；已获得合法开奖到核心落库/结算目标≤1s；实时决策计算/持久化目标≤5s；在有效赛前截止前完成冻结；正常可用期SHADOW不漏期；后台继续；主链出手频率目标≥30%、最低目标15%。

分别记录 request→durable-return、first-valid-observed→settled、deadline→freeze、应有机会→实际冻结覆盖，不能用其中一个代替另一个。断网、设备停机、系统限制、数据不合法和无模型须保留在完整机会分母并单列原因。无法合法事前冻结的期必须失败可见，禁止事后补成功。

出手频率是优化目标，不是强制下注配额。只有合格策略才进入唯一真实门；合格后必须在下一次合法调用中被检查、选择或给出可复核拒绝原因，不得再被过期的全局开关永久压在零权重。用户主动关闭真实开关时必须尊重并明确显示该原因。自然优势与代际提高需要未来证据；工程验收不能保证每代或每次预测更强。

## 8. 变更合并和回滚

同一文件的修改按B01→B12顺序累积，文件卡保存前后哈希、方法级意图和来源问题；下一批以实际前一批提交为before，不能重复套用122或152的整文件后态。每批独立完成本批合同回归并构建；B12只负责全链集成和长时观察汇总，不替前批补做缺失接口。

回滚优先回退新模型/新规则/可关闭的新分支，不回滚已生效的数据schema到不兼容旧APK，不覆盖canonical和已结算证据。数据库迁移采用向后兼容的新增列/表及版本化读者；确需破坏性迁移必须独立备份、恢复验证并列为明确门槛。
