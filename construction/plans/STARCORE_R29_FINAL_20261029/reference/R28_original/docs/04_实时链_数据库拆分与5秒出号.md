# 04 实时链：数据库拆分与 5 秒出号

## 4.1 问题与根因（证据见 docs/00 0.3）

| 现象 | 数值 | 直接原因 |
|---|---|---|
| 请求→提交 P95 | 23,523ms | 冷启动只要 5,313ms；热运行变成 22,257ms → **不是算得慢，是在等** |
| commit P95 | 8,676ms（预算 50ms） | 实时链每期 4—5 次独立写事务，每次都要抢唯一写锁 |
| compute P95 | 12,540ms（冷启动 2,526ms） | 分析线程与 R26 专家/铸造线程同为 nice 0，抢不到 CPU |
| 首错分布 | 写失败 8、取消 7、超预算 5、域路由提交失败 3、canonical TX 失败 2、bundle capture 失败 2 | 写锁超时 `CP3_DB_BUSY_DEADLINE` → `F01_WRITE_FAILED` → 重试 → 过期 |
| 研究写等待 | >200ms 每小时 14,932 次 | 研究与实时同库 |

R27 的写队列只能约束 R27 自己；R26、R908、R932、报告导出各走各的写路径。**只要还在同一个文件里，就无法保证实时链拿到写锁。**

## 4.2 方案一：研究库独立（R28-010、R28-011）

### 新文件

`starcore_research_r28.db`，由新类 `ResearchDatabaseR28`（`SQLiteOpenHelper`，WAL，`synchronous=NORMAL`，`journal_size_limit=64MB`）打开。

### 迁移

1. 首次启动 R28：在研究线程上 `ATTACH` 旧主库只读，`INSERT INTO research.r27_x SELECT * FROM main.r27_x`，逐表比对行数与内容哈希；
2. 全部一致后写迁移回执 `r28_migration(table, rows, sha256, at)`，再在主库 `DROP TABLE r27_x`；
3. 任何一步失败：保持旧表不删，R27 继续用旧位置，报告 `MIGRATION_PENDING` 原因（不阻塞实时链）。

### 读写规则

| 谁 | 读 | 写 |
|---|---|---|
| 实时链（fetch/analysis/settlement） | realtime.db | **只写 realtime.db** |
| 研究池（ResearchPoolR27 工作线程） | research.db；开奖与结算行通过**只读连接**读 realtime.db（WAL 允许并发读） | **只写 research.db**（经 `ResearchWriteQueueR27`，改为绑定 `ResearchDatabaseR28` 的写协调器） |
| 主链衔接 `MainlineBridgeSU2` | research.db 只读：ACTIVE 证书、对应冻结 | realtime.db（意图交给 DecisionGateEngine，原路径） |
| 报告/图表 | 两库只读 | 报告任务文件 |

`ResearchWriteQueueR27.p0Writing()` 的"让路"逻辑在分库后可以删除：研究写不会再阻塞实时链。保留 `freezeWindow` 只用于 R27 自己的冻结批优先于其他研究批。

### 为什么这样最有效

SQLite 一个文件只有一个写者。两个文件就是两个写者，互不等待。实时链每期写入量很小（几十行），独立后 commit 应回到冷启动水平（~120ms）。

## 4.3 方案二：实时链写事务合并（R28-012）

当前每期顺序执行的写事务（源码）：

1. `AnalysisRequestStoreR36.bindHistoryHash`（`R36_ANALYSIS_HISTORY_BIND`，第742行）
2. `commitCanonicalBundleVerifiedR368`（canonical bundle）
3. R932 bundle capture（`R932_BUNDLE_CAPTURE_COMMIT_FAILED`）
4. R932 domain route（`R932_DOMAIN_ROUTE_COMMIT_FAILED`）
5. 状态推进（request → frozen → canonical）

R28：新增 `IssueCommitR28.commit(store, request, lease, result, snapshot)`，在**一个** `BEGIN IMMEDIATE` 事务里完成 1—5，任何一步失败整体回滚，失败原因按步骤记录到 `r28_issue_commit_failure(step, code)`。R932 domain route 若只服务已退役的 R932 研究链（R28-022 核对），则直接删除该步。

验收：`F01_WRITE_FAILED`/`CP3_DB_BUSY_DEADLINE` 在实时链 24 小时 = 0（M05）；commit P95 ≤200ms（M02）。

## 4.4 方案三：CPU 优先级与线程（R28-014）

| 线程 | 现在 | R28 |
|---|---|---|
| `eth_k3_analysis_channel`、`eth_k3_fetch_channel` | R27.4 已升前台 | 保持 `THREAD_PRIORITY_FOREGROUND`（−2） |
| settlement / `starcore_r908_settlement_recovery` | DEFAULT | `THREAD_PRIORITY_FOREGROUND` |
| 研究池 | BACKGROUND | BACKGROUND（10），线程数 = `availableProcessors()−2`，最少 2、最多 6 |
| R26 专家/铸造 | 普通 `new Thread` | 删除（docs/03） |

另：分析开始到冻结完成期间，研究池把活跃线程降到 1（R27.2 已有），R28 保留。

## 4.5 方案四：观察池冻结的"准备—冻结分离"（R28-013，完成 R27-008）

R27.4 每期要为 24 个观察算法冻结，R28 要扩到 128+16 个。做法：

1. 开奖 t−1 落库后，研究池**立即**用增量特征（docs/05 5.3）计算全部观察算法对 t 期的 K3，放在内存 + `r28_prepared(target, policy, k3)`；
2. 冻结截止前只执行一次批量 INSERT（144 行，<20ms）；
3. 若准备晚于截止，记 `PREPARE_LATE`（不补冻结，PIT 红线不变）。

验收：观察冻结完成率 ≥99%（M22）；冻结准时率 ≥99%（M03）。
