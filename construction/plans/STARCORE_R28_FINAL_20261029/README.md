## 1. 先说结论（请先读这一节）

### 1.1 为什么"做了好多版本，始终没做好"

不是某一个 bug，是三件事叠在一起：

1. **开奖数据里没有可利用的规律。** 这是胜率上不去的根本原因，任何版本都改不了。最新报告自己的数据：
   - 严格样本外 313 期，命中 93 次 = **29.7%**（随机基线 30%，保本线 30.3%）；
   - 24 小时内进化 553 代、尝试 35,713 次、产生 33,769 个不同策略，**留出数据上被证实的提升 = 0**；
   - 当前冠军留出命中 **26.9%**（第513—552代一直是同一个冠军，因为没有任何挑战者通过验证），同期"随机选号"对照 24%—34%（中位 29.6%），"打乱标签"对照 21%—37%（中位 27.1%）——冠军并不比瞎选好；
   - 回放挑选段上幸存者命中 38%—45% 看起来很高，但 33,769 个零优势策略各跑 512 期，"运气最好那个"的中位数就是 **38.5%**（本方案 `tools/r28_independence_audit.py` 实测）。这就是"历史上看着很强、一到实盘就掉回30%"的原因；
   - 60 个观察算法逐期实盘：逐期合计 1,651 期命中 507 次 = 30.7%；按各自规则真正"出手"的 659 次只命中 176 次 = **26.7%**（"挑时机出手"反而更差）；
   - 本方案对仓库1万期数据再做一次独立检验：重复排列 13 个（纯随机期望 13.8 个）；前半段找到的"最强关联"拿到后半段逐期使用，命中 **29.6%**。详见 `docs/01`。
2. **软件太大、三代系统同时在跑、互相抢资源。** 1,146 个 Java 文件、约 50 万行；同一个 SQLite 文件里 603 张表、240 万行、1.7GB；R908、R9xx/R26、R27 三套研究系统并行，进程里 79 个线程。结果：出号 P95 **23.5 秒**（目标 5 秒）、每小时 **14,932 次**写等待超过 200ms、24 小时错过冻结截止 46 次、研究 CPU 只拿到相当于**单核 9.5%**、13 个任务从未运行。这是"运行不流畅、模块冲突"的根本原因。
3. **施工方案越写越大，永远闭不了环。** 1832 条需求 0 条验证；R27 的 58 张卡 42 张"已修改待设备验证"、16 张未施工。每一版都在旧系统上叠新系统，没有删除，所以每一版都更慢、更难验证。

### 1.2 R28 承诺什么，不承诺什么

**承诺（全部可在真机报告里逐项核对，见 `docs/09` 的 43 项验收表）：**

- 出号 P95 ≤ 5 秒、冻结准时率 ≥ 99%、主线程不卡顿、写入失败为 0；
- 只保留一套研究系统，研究 CPU ≥ 0.5×研究线程数个核（亮屏充电时），从未运行任务 = 0；
- 每期都用全部历史数据实时回放训练、变异、融合、淘汰；128 个观察算法 + 16 个负对照每期都有真实冻结与结算记录；
- 深度学习用 ≥ 5 万条历史样本预训练、每期续训；原子、矩阵、校准、消融全部产出数据；
- 检测报告新增三章，**自动回答**"胜率为什么低""每个功能效果怎样、为什么不够强""下一步怎么改"，每个结论都能回溯到数据行；
- 一旦数据里真的出现可利用的优势，系统能在统计上站得住的最短时间内识别它，按现有主链规则送进主链。

**不承诺：** 35%/37%/40% 的胜率。按上面的数据，最可能的真实结果是"未发现显著高于 30.3% 的稳定策略"——这是正确的测量结果，不是故障。本方案不会为了让数字好看而放松测量（例如把回放成绩当实盘、删掉负对照、降低主链门槛），因为那样做只会让真实下注亏得更快：按 +6.9/−3.0 计算，30% 命中时每注期望亏损 1%。

按 `docs/08` 顺序：**B1 数据库拆分 → B2 退役旧系统**（这两批做完，出号慢、写等待、研究饥饿、线程过多会一起消失）→ B3 研究满血 → B4 深度学习/原子/矩阵 → B5 报告 → B6 图表 → B7 真机与发布。B1+B2 是"最小可见里程碑"，完成后第一份真机报告就能看到 M01—M13 大幅变化。
