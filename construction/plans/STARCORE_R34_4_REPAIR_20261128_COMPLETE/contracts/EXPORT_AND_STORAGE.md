# 报告可导出与存储回收专项合同

## 1. 本次准确状态

原上传 ZIP 为 19,471,817 字节，内层 `STARCORE_FULL_REPORT.zip` 为 19,744,957 字节。外包和内包 CRC 检查通过；清单登记的 56 个载荷逐项字节数与 SHA256 一致，另有 `ARCHIVE_MANIFEST.jsonl`，内包合计 57 个文件。因此本次不是“压缩包根本没导出”。

内部 96 项检查只有 56 项执行，40 项 READ_ERROR，全部是 REPORT_CHECK_TIMEOUT；`checksComplete=false`。诊断包未附约 5.06 GB 的 SQLite 原库、安装 APK 和全部模型/训练原字节。报告可用来定位已观察的问题，但不能凭此完成用户数据库全量重放。

`STORAGE_CENSUS.txt` 的采样是文件占用，**不是内存 RAM**：总 31,180,341,650 字节；REPORTS 24,546,120,422 字节；其中报告/保留快照 24,109,711,360 字节。各计数发生在区间采样中，不能与较早 runtime DB/WAL 瞬间值强拼成一个原子快照。

## 2. 不得改坏的导出行为

保留现有压缩包命名、`index.json`、内部清单、文件 SHA、分卷与单卷选择、缺省体积限制、语义回执及 SAF 交付。报告应允许导出真实失败/UNKNOWN，不应以“检查没全通过”为由拒绝让用户拿到诊断包。界面必须分别展示打包完成、检查完成、检查健康和业务验收。

本轮的检查预算、SQL和依赖缓存修复不能改变校验语义，不能删除慢检查、给超时填0、把 READ_ERROR 改 PASS，也不能使用历史缓存伪装本次数据。

## 3. 检查超时的最小修复

### 3.1 等价优化覆盖率查询

`RuntimeHealthLedgerR36.readCoverageR342` 的第一条 min(target_issue) 查询出现在 RSEC-009 超时堆栈。已有 `r341_observation_release` 索引可按 release/source/database 缩小范围。候选补丁从 scope 驱动联表，完整保留 event_id 关联、game、12位合法期号与 min 语义。

随包脚本已在主机 SQLite 夹具验证返回等价和候选查询计划；目标 Android SQLite 的执行计划及原 5 GB 快照耗时仍必须测量。若当前设备优化器已选最优计划，不应仅因补丁名就宣称性能修复。其他 30 期 EXISTS 查询逐条检查索引，禁止通过任意裁掉历史事件来“提速”。

### 3.2 失败依赖只计算一次

`ReportReadContextCP4.memo` 当前只缓存成功值；共享 model-analysis 超时会被下游检查再次发起。改为本次不可变报告会话内的结果封装：`SUCCESS(value)` 或 `UNAVAILABLE(typedReason, originalFailureRef, dependencyKey)`。缓存键包含快照身份、生产版本和真实参数。每个下游检查仍产生独立结果，显式指向同一依赖失败原件。

不得把异常对象连同失效 CancellationSignal 跨会话复用；不得给全局缓存永久记“不可用”。用户对同一快照显式续跑时建立新的 attempt，已满足前提的失败依赖可按重试策略重做，原 attempt 的结果不被覆盖。新快照不继承旧失败或旧成功值。

这些 typed 状态只在内部依赖容器使用。211 的 `ReportCatalogCP4.CheckResult` 对 `execution_state` 只接受 `EXECUTED / READ_ERROR / CANCELLED`，必须保留：依赖来源不可用映射为现有 `READ_ERROR`、`domain_outcome=SOURCE_UNAVAILABLE`、`health=UNKNOWN` 与原 `errorRef`；全局取消保持独立 CANCELLED。不得把 UNAVAILABLE、PAUSED 或 NOT_STARTED 直接塞入该枚举，避免被校验器再变成伪读取错误。

### 3.3 消除总预算的级联饥饿

`ReportCatalogCP4` 当前以共享180秒余量决定每项预算，最低1秒；前部耗尽后后38项只剩1秒。不要简单把180秒改成无限。按检查的已声明成本给各项独立上限，共享依赖去重后继续独立检查；本次总体预算不足则写“待续跑”与精确游标，在同一 immutable snapshot 的下一次 attempt 继续。

完成态从96项实际状态计算，不从循环走到末尾计算。全部超时/跳过项保留原编号、原因、依赖和预算。续跑完成后产生新的结果版本并链接原结果，不能改写旧失败原件。

PAUSED / NOT_STARTED 仅属于 job/check-progress 的可恢复内部进度；对外 catalog 仍装配原96项与既有执行枚举，尚未取得结果的项明确给出缺来源/待续跑原因且不算 `completes_contract`。如果需要交付当前部分诊断，依照原失败可导出语义生成诚实结果，不改现有格式。DIAGNOSTIC 能否进入 READY 和回收工作文件依照原请求范围、ZIP/清单/语义完整性，不额外要求所有业务检查通过，也不增加 `checksComplete=true` 或 `allChecksPassed=true` 才能交付的门槛。

### 3.4 取消与连接所有权

保留当前每次检查创建并清理 CancellationSignal 的正确实现；没有证据表明本次是旧 signal 直接复用。改造 memo/续跑时增加回归：超时发出取消后，必须确认对应 worker 停止使用该连接，再复用或关闭；若有界退出未确认，隔离该连接并显式记未知，不能让下项在同一连接并发重入。不同检查可使用指向同一不可变快照的独立只读连接，但不复制一份新快照。

## 4. 快照回收与原件保全同时成立

当前 `ReportPublicationCP12.pruneTerminal` 跳过存在 snapshot.db 的 FAILED 作业，`ReportCleanupR31` 主要处理 READY_TO_SHARE。失败原件保护是合理约束，缺口是缺少可证明的恢复/退役路径；不能直接删除全部失败快照。

第一步采集各 job 的完整状态、snapshot hash/bytes、创建时间、活跃 reader、所有附件/恢复引用、现有ZIP/语义回执、cleanup原因。本诊断包没有五个大快照各自的 job.json 原文，不能断言五份都是 FAILED，也不能按文件年龄猜测可删。

|作业类型|允许的后续动作|删除快照前必须成立|
|---|---|---|
|仍在生成、分享或恢复|继续同一作业并持有引用；取消按原状态机处理|活引用未解除时不可删除|
|READY_TO_SHARE|验证当前最终ZIP、清单和语义回执，恢复现有清理队列|原件需求已由可读、哈希一致的交付物满足，且无其他恢复引用|
|失败且本快照是唯一原件|优先用同一快照续跑诊断；或将精确原库/必需闭包转存到已验证的持久位置|替代原件字节级完整、读取校验成功、恢复引用切换完成；新诊断的摘要不等于原DB替代品|
|已有精确替代原件|由独立退役回执记录替代物、源hash和引用核销|旧失败事件/回执保持原样；报告作业可按既有状态机在新attempt真实恢复为READY，不能伪改旧attempt成功|
|引用不清或校验未完成|继续保留，显示阻断及需要的验证动作|不能以最新一次成功、超过24h、目录名旧等理由删除|

新增退役回执应走现有持久迁移/存储 owner，具备单调状态、幂等键、哈希验证、重启恢复和只删除精确匹配文件的保护。多个进程不得各自判空后同时删除；引用释放与实际文件清理分步落盘，失败可重试，原件替代物在清理后仍可回读。

报告作业在同一快照真实重试成功进入 READY 后，按原 request profile 判定工作快照是否仍需保留：DIAGNOSTIC 在完整完成所请求范围、现有 ZIP/清单/语义验证通过且无额外原件恢复引用时，沿现有 `requireRawCoverageR31` 和 `cleanRaw` 合同释放工作快照，不能给默认诊断模式凭空增加“必须把5GB原库塞进ZIP”的条件。FULL_RAW 或仍有独立原件恢复引用时，才要求同hash原库替代物。前者是完成原请求后的工作文件退役，后者是原库原件的替代证明，两种理由不能混用。

用户重试同一个失败导出时，优先继续其固定快照而非再复制5GB。全新诊断请求若需要新水位，不能伪装复用旧水位；应做空间预检、限制并行快照数量、先处理已可验证的回收债务，并给出真实等待原因。

## 5. 5000热历史与全盘预算

draws 的5000限制只约束开奖表，不能自动约束 runtime_event、scope、chart cache、故障原件与报告快照。按实际 owner 和引用分类设置热区预算及分片归档：活动冻结模型、未结算义务、有效资格、活跃回放pin、父代/检查点、报告恢复快照均不得提前释放。

归档采用“写替代原件→读回验证→登记manifest与引用→核销热引用→有界清理”的顺序。不存在完整引用闭包时不清理；不存在足够空间时不能再制造一份更大的临时备份。VACUUM/数据库交换只在已验证恢复和合适维护窗口执行，不能代替业务逻辑修复，也不能放进赛前写锁。

故障队列的共享热配额需要可前进的归档机会及独立控制槽。背压仍保护实时事务，但该背压必须能被实际成功排空解除；容量丢失作为已发生的诊断缺口保留，不清零伪装没有发生。

## 6. 报告功能不可退化验收

|场景|必需结果|
|---|---|
|相同安装连续5次正常导出|每次均得到可读ZIP/index；SHA与语义回执相符；可清理作业的快照不按次数永久累加|
|慢查询/共享依赖失败|96个编号完整，失败引用清楚，独立检查继续，输出诊断包可分享|
|用户取消后重试|取消态明确，旧worker停止，重试有独立attempt，原作业/原件不被悄悄覆盖|
|进程在写ZIP中途退出|不发布半成品；从已持久阶段恢复或产生明确失败包；重试不重复复制巨大快照|
|分享后进程退出|交付URI继续按原有效期可读；不能在消费者读完前清理ZIP|
|低磁盘/配额压力|不删活引用原件，不无限复制；最小诊断与恢复原因可得，空间条件恢复后可续跑|
|故障队列满|Critical仍按既有规则准入，排空/归档有实际进展；报告/遥测不递归放大故障|
|当前/历史scope|完整JSON可解析；snapshot/PID/boot/source/database一致才可拼接；历史原件不冒充当前健康|
|大库真实回归|原5GB级快照或等价脱敏副本上逐项测量时延/内存；主机夹具不能代替此项|
|新旧模式兼容|默认诊断、完整原件模式、单卷/分卷、外部SAF和内置分享都保留；不能用删模式解决大小问题|

每个场景同时测主链预测与结算是否被报告拖慢。报告读取应使用不可变快照；分析、压缩、校验和文件传输不持有实时 writer。

## 实际快照pin回调的实现边界

R344-008要求改到`app/src/main/cpp/report_native_cp4.c`的`cp4_backup_impl`真实BEGIN/schema pin窄区间，并贯通JNI、`ReportNativeCP4`及其`sourceControlR31`包装层；包装层必须转发可选采样回调。保留原memory/backup/cancel/磁盘准入行为，不改vendored SQLite或Zstd。旧native `CLOCK_MONOTONIC`不得直接与Android `elapsedRealtime`比较，使用同域Java回调或已验证的`CLOCK_BOOTTIME`并绑定boot身份。

采样失败仅使新投影保持UNKNOWN，旧job无sidecar仍能按原协议导出。pin时点不做整库hash或长IO；备份结束后再绑定最终snapshot SHA/bytes并原子保存回执。休眠、取消、大库复制、主进程重启、旧job与空回调均列为施工后的JNI/Android反例，不以当前主机审阅冒签通过。
