## 2. 对参考 R31 的必要修订

5. **不能统一改成 `VACUUM INTO`。** 它在 SQLite 3.27.0 才加入；实际 Android/native SQLite 引擎版本须分别探测。它是一次性完整输出，不是低成本持续压缩。已有原生 backup 协议可增量执行，应优先保持。

## 3. 最小安全不变量

`R31-ST-I01` 所有新增文件/数据库增长路径必须在写入前取得分类预算，实际写入每个 chunk 再扣减；测量失败不得当 0 bytes。

`R31-ST-I02` 一个不可重建对象只可在没有有效根引用、没有运行者租约、没有未终结迁移、没有未完成发布依赖时回收。根包括当前/回滚主链、待结算冻结、未完成训练输入、开放验证段、证书证据、分享读者以及迁移原库。

`R31-ST-I03` 原件被回收时，其声明必须同时降级为 `SUMMARY_ONLY` 或 `EVIDENCE_RETIRED`；不得继续将它当可重放证书。正在主链应用的证书与所需原件不可降级。

`R31-ST-I04` 生产者、引用表、回收者共用现有单写入所有者；GC 的“检查无引用—标记 DELETING”必须在同一短事务内。标记后禁止新引用，文件 IO 在事务外，最终写入删除回执。失败重入以对象 hash/版本及删除 fence 判断，不能按路径名直接删。

`R31-ST-I05` 5000 期滚动原始开奖仍是最低热历史口径。历史训练需要更早数据时使用去重输入块与明确的短期任务根；不能让每个策略复制一份同样的历史，也不能让无消费者 pin 永久保留。

`R31-ST-I06` 旧版本进入迁移前已经超预算的受保护字节是 `INHERITED_PROTECTED_DEBT`。先停止新可选大对象、腾出可重建空间、保留关键抓取结算预留；不得为瞬间达标毁掉原件。

`R31-ST-I07` 允许持久研究持续执行，但工作集、活跃候选、同时持有的 checkpoint、图矩阵尺寸、后台排队、日志以及输出字节均有界。不能无限创造同时又要求永久保存全部原始产物。

## 4. 预算设计及饱和行为

以下为首轮工程目标，B12 必须在 V2353A 实测校准。单位均为 MiB，1 MiB=1,048,576 bytes。配额配置有版本/hash，不能运行中静默放大。

| 分类 | 常态目标 | 必须包含 | 到达高水位的动作 |
|---|---:|---|---|
| 热数据库 | 640 | 主表、所有索引、schema、freelist 文件长度 | 到512触发有界回收；释放可重用页；不可依赖“删行文件立即缩小” |
| WAL及sidecar | 64 | 实际所有活动库WAL；SHM单列但纳总量 | 收回超时读租约，PASSIVE checkpoint；满足连接边界后再尝试有时限TRUNCATE |
| 输入与研究证据CAS | 256 | 数据块、归档、未完成上传/替代份 | 内容hash去重、关闭已终结任务根、GC；拒绝新的非关键重复块 |
| 模型与checkpoint | 192 | 权重、optimizer/RNG、父子状态、临时模型 | 当前+回滚+有限候选；淘汰候选根后GC；保留明确的谱系摘要 |
| 已发布报告 | 192 | ZIP/分卷/index/manifest和分享保护 | 默认最近2份，计总bytes；正在读取的不能删，新大报告进入等待或明确失败 |
| 可重建缓存 | 32 | 已证明无权威用途的特征/显示cache | 按字节LRU与输入hash淘汰；清除后能用持久输入重建 |
| 诊断与其他 | 32 | 环形日志、收据、扫描元数据、临时小文件 | 有界滚动；错误按fingerprint聚合，保留最近原始样本与总数 |
| 常态验证备份 | 128 | 有明确恢复证明的旧备份 | 原件若超过此值计保护债务，不能直接删除；替代备份恢复验证后迁出/回收 |
| **常态合计** | **1536** | 所有分类相加，detail子项不重复相加 | 80%触发，低于70%退出，避免频繁抖动 |

常态硬预算建议 2048 MiB，差额512 MiB作为关键业务和历史保护债务缓冲；导出/迁移另设互斥的暂存 reservation。首轮导出峰值目标≤3072 MiB、绝对写入准入上限≤4096 MiB，并且系统可用空间须保留至少256 MiB或当前关键业务实测24小时需求（取大者）。这是设计准入上限，不能伪装为原生 SQLite/文件系统绝对不会多分配一页；每个允许增长的写操作必须有最大增长量和失败回滚路径。

导出 reservation 不是固定“2×主库+64MB”后不再管。按实际格式计算 `snapshot_upper_bound + detached_facts_upper_bound + compressed_archive_bound + delivery_zip_or_parts_bound + metadata + safety_margin`；同一字节阶段不同时共存才可共享 reservation。每个流式写入器在写前检查剩余预算，超过时取消当前导出、保留唯一恢复原件并安排清理，不拖累开奖事务。大原始数据导出如果空间不够，明示 `EXPORT_SPACE_REQUIRED`，不得生成声称完整的截断包。

物理余额与逻辑余额都要测：delete后数据库可重用页增加可缓解新写，但用户看到的文件长度可能不变。报告必须同时显示 `live_file_bytes / reusable_page_bytes / allocated_blocks_bytes(if available) / os_free_bytes / pending_cleanup_bytes`。正常稳定阶段按第2/3天净增量及对象数量上界验收，不以某个一次性峰值截图宣称有界。

## 5. 对象、引用与回收协议

新增 `StorageBudgetR31`、`StorageLedgerR31`、`EvidenceReachabilityR31`、`StorageGcR31`；在 `ResearchRetentionStoreR30` 中作为替代的统一实现，不另启动第二套所有者。建议表：

* `r31_storage_reservation(reservation_id, owner, category, requested_bytes, used_bytes, state, owner_fence, created_at)`：已申请未完成的峰值份额，最终完成/失败必须释放；进程死后只由恢复者按owner_fence接管。
* `r31_artifact(hash, kind, bytes, relative_path, state, generation, created_at, last_verified_at)`：hash内容地址唯一，禁止同内容复制多个目录计作独立资产；同hash存在多个副本时至少一份已验证后才删冗余。
* `r31_artifact_edge(parent_hash, child_hash, contract_hash)`；`r31_artifact_root(root_id, artifact_hash, root_type, owner, owner_fence, state)`：从根计算引用闭包。hash只是身份，不是内容已验证的证明；恢复时必须检查bytes/hash/codec。
* `r31_gc_action(action_id, artifact_hash, expected_generation, delete_fence, phase, reason, before_bytes, after_bytes, evidence_hash, error)`：阶段 `CLAIMED → DETACHED → UNLINKED → RECEIPT_COMMITTED`。GC必须先有持久删除权，再在事务外unlink。
* `r31_storage_sample(sample_id, start_mono, end_mono, clock_boot_id, category, file_bytes, reserved_bytes, reclaimable_bytes, protected_bytes, method, completeness)`：5分钟全量增量census/异常时立即采样，保留288点滚动+30日小时汇总；样本key、类别枚举及表数固定有界。

GC顺序：取得存储所有者→收集有效根→有界可重入标记→同一写事务再验证registry版本并把未达对象置DELETING→阻止新edge/root→打开删除目标校验identity→同目录重命名隔离或直接unlink（遵守源文件lease）→写删除结果→重新测量。应用重启后先恢复GC journal；不把“已写删除计划”当成已释放磁盘。引用循环无根时可回收；有根环整体保留。不能让CAS文件被删而SQL locator仍声称可读取。

保护根也必须有结束契约：训练任务只有输出checkpoint和cursor同事务提交后才能释放输入根；取消任务先撤销fence并等待计算停止，再关闭根；模型主链替换先把旧模型降为回滚根，经过预设回滚窗口且无证书依赖再释放；永久保留的是有限冠军/重要谱系及必要证据，失败候选只保留有限时间原件和可解释摘要。所需保护根本身超过预算时应返回 `BLOCKED_PROTECTED_BYTES` 并列出最大根的释放条件，不能隐性丢证据。

## 6. keep 表迁移与已有协议复用

`ensureProtected` L23–48 当前创建/检查55个现场表和相关触发器；开头的DDL及每表元数据检查不能在每次retention slice内重跑。B02将DDL移动到版本化迁移所有者；B05替换“任何删除都永久搬家”为分类证据生命周期。

迁移必须逐表进行：读现场schema与实际trigger SQL→建立表政策及consumer/producer清单→标记待迁移版本→按稳定主键/row generation有界复制需要保留的原件到CAS并校验→新表对象/引用/覆盖回执提交→短事务切换该表删除授权触发器→新/旧读路径对比→确认旧reader已退出→移除仅已迁移行→最后才DROP空keep表。不中途将全部触发器先DROP。

保留统计累加要精确定义：命中计数是可加的，但分位数、置信区间、父子差异协方差、漂移检测状态、策略选择偏差、校准曲线不能用一个sum无损重建。每种汇总必须列“能回答/不能回答”；证据退役后不得仍授予高品质资格。主链证书依赖的冻结预测和真实结果可以紧凑编码，但不能只剩hash。

现有 `DataRetentionGovernorR900` 的页归档、publication、版本校验、pin保护、归档到期、孤儿revision清理值得保留。`STALE_PAGE`增加table/row_count/expected_generation/observed_generation/schema_hash/时延/重试次数；连续3次同页失败，重新准备更小的稳定终结行页（64→32→8），保留旧请求终结原因，跳过仍在变化的行并记录等待；不循环创建无界新snapshot。每个任务最多一个未完成归档请求，采用request_id幂等续作。

事件表保留不可用“直接DELETE LIMIT 500”绕过guard。现场 `catalog-0003.jsonl` L1360 已将 event no_delete guard 改为需verified archive permit；最初类的无条件guard不是运行schema真相。R31迁移测试要覆盖旧/新安装、重启后ensure重复调用，确保guard不会退回无条件且不会被整体删除。默认对同issue同event_type同fingerprint的高频诊断合并计数，仅关键状态转移、freeze/settlement/learned证据保持逐条；摘要明确区分业务事件和采样诊断。

## 7. 报告生命周期返修

保持原 `publish` 的“校验→ZIP→quota→published指针→READY→cleanRaw”顺序。新建独立 cleanup work item，由同一报告所有者提交，待所有 `SQLiteDatabase/Cursor/Native backup/InputPin/InputStream` 关闭后执行。cleanup state不是报告结论：报告可以 `READY_TO_SHARE + CLEANUP_PENDING`，但该pending有实际bytes、attempt、next_retry、last_error、protectedReason及计入全局预算。

恢复的删除范围必须以封存delivery的manifest覆盖为条件。普通诊断报告原本不含raw DB，可删除私有snapshot是因为发布契约明确只保证诊断材料，不能说“ZIP可恢复完整软件数据库”。如果用户选择FULL_RAW，必须确认ZIP或全部分卷包含对应raw member并验证再删本地重复副本。校验失败不能按24小时一到就删除唯一未验证原件；应限制新导出、告警并有恢复入口。用户明确取消的未发布任务可按取消协议清理，不影响另一个已发布包。

`publishedBytes` 保留交付体积指标，另加 `jobPhysicalBytes`，不能混用；全局配额遍历所有 jobs/当前/暂停/失败/清理pending/recovery/saf-parts，另计未登记临时对象。发布后及分享结束后触发cleanup，不必等下一次导出才回收。GC不删除有实际share lock的文件；软分享24小时可以通过策略等待，但不能扩展为无限保留。一次点导出仅一个工作owner；重复点按request key合并或排队上界3。

源码调用索引37MB可按source commit生成一份可验证共享资产；每份紧凑报告携带版本hash、相关文件/方法片段及可用性说明。若“离线完整源码映射”是选定的导出契约，就应在包内包含真实索引或单独随包资产，不能只提供一个可能打不开的链接然后称完整。诊断范围25MB通过规范化字段与流式JSONL去重；必须维持表/检查数量及逐项状态，不砍掉UNKNOWN行。

## 8. 真正释放磁盘与离线重建

当前 `StorageMaintenanceServiceR82` 明确是离线维护：request会设置user_enabled=false并停止AutoFetchService，完成后不自动重启。不可将其作为日常保留任务直接调用，否则正好再造“后台不运行”。常规生命周期GC、分批删除、checkpoint需在服务运行时有界执行；离线重建仅用于旧库物理尺寸治理。

新建库可配置incremental auto_vacuum；既有库切换需要重建/迁移，不能只改PRAGMA便声称生效。检查目标SQLite实际version/compile_options/native引擎版本，并记录。正常checkpoint使用PASSIVE统计busy/log/checkpointed，读租约过期用CancellationSignal取消该reader而非强关别人连接；只有无长读、关键写空窗且deadline足够才尝试TRUNCATE；超时立刻让路。

离线重建复用 `StorageMaintenanceFileR82` 的可恢复swap journal，不直接VACUUM原库。预先检查最大空间、当前pending任务、原库hash、业务rowid依赖；因为VACUUM可能改变没有显式INTEGER PRIMARY KEY的ROWID，所有 `research_row_revision_v2` / archive member / row locator 必须重映射或证明原生rebuild保留对应rowid。完整性校验不能仅 `quick_check`，还要逐表schema、行数、主键hash、BLOB字节hash、证据引用闭包、待结算冻结数和主链模型加载。

旧备份删除先核实没有pending swap、当前库启动/恢复验证通过、原库hash与receipt一致、所选回滚策略已满足。`deleteVerifiedBackup` L109–113 当前检查旧备份hash及receipt；R31补充“新库运行恢复回执”绑定，不按文件年龄或只看receipt存在就自动删。迁移中断任一阶段应保留至少一份可验证原库，不能两头删除。

## 10. 官方技术依据（2026-11-04读取）

* SQLite VACUUM：<https://www.sqlite.org/lang_vacuum.html>。本设计仅引用其VACUUM需重建、额外空间、ROWID变化和事务限制；正常DELETE的可重用页不等于文件收缩。
* SQLite WAL：<https://www.sqlite.org/wal.html>。本设计依据单写者以及读事务end-mark对checkpoint的约束，不能靠另开writer连接实现并行写。
* SQLite DBSTAT：<https://www.sqlite.org/dbstat.html>。必须编译 `SQLITE_ENABLE_DBSTAT_VTAB` 才可用；dbstat只涵盖B-tree页，freelist/pointer-map等需另计。
* SQLite 3.27.0发布记录：<https://www.sqlite.org/releaselog/3_27_0.html>。确认VACUUM INTO新增版本，作为能力探测与fallback设计依据。

以上事实与应用特定的故障结论分开。SQLite通用限制可以验证实现设计，但不能证明这台手机的30GB具体来自哪张表。

## 11. 附带可执行契约模型

`storage_contract.sql` 与 `verify_storage_contract.py` 是可独立运行的 SQLite 协议模型，验证预算申请互斥、chunk超额拒绝、reservation原子转移、根引用闭包、GC与新pin先后竞争、未完成对象保护以及删除计划不冒充已unlink。它们不是Android迁移脚本，真实接入仍须使用现有单写者、owner/fence、文件锁及schema版本。运行 `python3 verify_storage_contract.py`；本次12项通过，回执见 `storage_contract_receipt.json`。它不证明真机72小时空间目标已经通过。

## 12. 堆、native、PSS与内存持有者的有界治理（B05-S11）

本节处理进程内存，与上述磁盘预算分别计量。新增能力不得仅以磁盘清理回答“内存无限增加”。已核实的源码风险：`ResearchPoolR27` L66 的 compute 使用未设置容量的 `LinkedBlockingQueue`；`ResearchWriteQueueR27.Batch` L34–35 的 `ops` 与bind参数在内存中累计，未见本容器自身的条数/字节上限；`ChartsActivityR83` L30 使用单线程executor，L105–145刷新取消旧future后继续提交，取消并不证明旧任务已离队或闭包已释放；当前一次性加载 `List<Panel>` 后交给UI，L127捕捉OOM仅是事后降级。`ReportExportServiceCP4` L23 已对native decoder与backup分别设4MiB/32MiB预算，应保留；仍需合并同时存活阶段的预算，且L531的 `readR27Summary` 将整个文件收集进ByteArrayOutputStream，需要读取上限/流式解析。以上是已看到的设计风险，不据此虚构本机已泄漏多少MB。

### 12.1 动态阈值与许可池

新增 `strategyv2/MemoryBudgetR31.java`，由 `RuntimeCoordinatorR26` 创建一个application-scoped实例，注入唯一ResearchPool、ReportExportService和图表repository；禁止每个模块各建一份“全额预算”。API：`tryAcquire(owner, kind, estimatedBytes, cancellation)` 返回可关闭Lease或结构化WAIT；`lease.grow(delta)` 在大数组/BLOB/解压chunk分配前执行；`close()` 幂等且只由实际持有者释放。记录active bytes、queued bytes、owner、fence、allocation kind、estimated/observed区别。许可池追踪的是已声明工作集，不能宣称等于JVM真实堆；实际heap/native/PSS另采样，发现偏差需修正估计。

令 `M=Runtime.getRuntime().maxMemory()`，`H=totalMemory-freeMemory`。首轮建议Java heap高水位0.75M、恢复水位0.60M、紧急水位0.90M；均为设计参数，须由B12按设备校准，不能写成实测固定96MB。预留新增实时工作量为 `max(0.15M, 已测关键链P99增量)`，UI与系统桥接也预留实测增量；研究可申请额为高水位余量扣除这些未分配峰值及现有有效reservation。若热启动基线本身超过高水位，报告 `BASELINE_CAPACITY_UNMET`，先找持有者，不能不断扩大largeHeap或预算。超过软水位先清未引用可重建cache、缩小replay/matrix批量并降低并行；达到硬水位停止新的可选大分配，保留抓取/结算与最小checkpoint路径。

native内存不以Java maxMemory作硬限。使用实际decoder、backup、direct buffer、SQLite连接/页cache、bitmap的登记预算总和，并采样 `Debug.getNativeHeapAllocatedSize()`、`Debug.MemoryInfo`/dumpsys PSS/RSS及系统lowMemory。PSS含共享页，不能与Java heap/native heap简单相加；它用于总进程趋势与OS压力判定。模型所需工作集无法容纳时返回 `MODEL_MEMORY_CAPACITY_UNMET`，改用可证明等价的分片推理/计算或拒绝该模型上线，不能隐性截断权重。

### 12.2 有界队列、共享输入、取消释放

新增 `strategyv2/BoundedResearchExecutorR31.java` 替换ResearchPool的unbounded compute队列：初始容量 `2*workerCount`，同时约束queued payload字节；拒绝返回 `QUEUE_CAPACITY_WAIT`，任务ID留在现有持久任务表等待，禁止CallerRuns把计算挪到实时/UI线程，也不静默丢任务。入队对象只含task key和小参数，5000期数组、模型权重不捕获进每个lambda。显式取消的未启动future立即remove；运行中任务只在poll确认停止、finally关闭资源后释放lease。`cancel(true)`、超时、Thread.interrupt都不是“释放成功”的证明；不响应取消的线程继续计入占用，禁止再拉起同owner副本。

新增 `strategyv2/SharedFeatureStoreR31.java`：以dataset hash、PIT cutoff、feature ABI、normalizer版本作为键，单份不可变primitive block供多个候选只读共享；采用bytes-LRU和显式reader lease，引用计数降零后才可驱逐。训练器的可变optimizer/model state必须独占，不能错误共享导致交叉污染。cache总量随M动态设上限，过期输入/候选淘汰/会话结束按owner释放；候选注册表、父代映射、ThreadLocal token与listener都要有终结释放路径。`ExecutionBudgetR26.enter/leave` L6–7须所有调用者try/finally成对执行，线程池复用不残留上一任务token。

写batch同时限定op数量和bind字节，初始每片64个op、每片bind上限 `min(256KiB,M/512)`，这些为待压测参数；大模型使用校验过的CAS流式文件和短事务指针提交，不能为了分片破坏既有CAS/fence/原子输出契约。计算先分片产生结果，不把整代所有候选的全部数据一次组装成一个Batch。多图加载按可见panel分页/keyset查询，一次只持有当前页与下一页，repository提供有界DTO，UI按像素宽度可解释降采样；研究原始数据留在typed表，禁止为了绘图把全库读到内存。刷新请求以最新generation合并，上一代cancel闭包移除，Activity退出取消callback并释放panel/view/bitmap引用；只释放自己拥有且无人使用的资源。

### 12.3 连续研究、CPU与温控

内存许可池与B01调度统一：达到软压力仍给每类持久任务短切片、公平轮询和最小必要checkpoint机会，批量与并行动态降低；恢复水位后自动续跑。严重OS lowMemory或热保护下允许短时停止大分配/计算，定期复核并记录可恢复条件；不能永远停在 `setResource` 字符串。连续2分钟没有解除时报告最大持有者、wait age、预计释放点，触发owner级取消/缩片或明确容量不足；不通过无条件清除resource强行分配。禁止设“只充电/闲时才训练”作为常规逻辑，也禁止为了保持非0 worker无视OOM或系统温控。资源暂停、任务错误、代码缺陷必须分别记录，不能又把内存退让计为隔离错误。

### 12.4 新增验收

`ST-M01` 同时申请许可超过上限的并发测试，只有预算内申请成功；重复close不负数，异常/finally/取消/线程死亡路径可追账。`ST-M02` 注入1000个研究/图表刷新请求，运行数、队列条数、queued bytes始终有界，实时线程不执行被拒计算，待办不会丢。`ST-M03` 重复100轮进入图表—加载—退出与训练取消，Activity/Panel/共享数据块在真实使用结束后不可继续被池队列/Handler持有；用heap dump/dominator证实，而非只看一次GC后的数值。`ST-M04` 同一输入并行64候选时共享输入物理实例为1，模型可变状态互不污染。`ST-M05` native压缩/backup取消或异常后native预算与实际存活资源回到基线包络，FD/SQLite连接数无阶梯增长。

`ST-M06` 72h在同一设备/同一版本记录Java live heap、native、PSS、GC pause、FD、线程、queue bytes和最大owner；按warmup后对等负载窗口比较。验收首先满足所有容器/队列/许可硬上界与OOM=0；其次检查稳定工作负载下live-set/PSS趋势无持续正斜率，若模型数量改变按预先规定的容量包络解释，不允许事后把泄漏称“学习资产”。建议回归门为末24h等负载P95 live heap不超过首个稳定24h的110%，同时绝不能越动态高水位；此为工程目标，必须记录样本数/基线/置信范围，未测试标NOT_RUN。GC可回收对象导致RSS暂时不回落不单独判泄漏，应结合dominator与重复负载稳态；强制GC只可用于隔离测试，不可在每期生产路径调用。
